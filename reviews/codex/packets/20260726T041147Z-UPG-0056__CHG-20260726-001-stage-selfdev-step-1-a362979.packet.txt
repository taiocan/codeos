    # Upgrade: governed-mechanism-activation-convention — Governed Mechanism Activation Convention
    
    **Priority**: P2
    **Status**: PROPOSED
    **Type**: downstream-doctrine
    
    ## Problem
    
    A future Codeos feature (the first known case: a "Controlled Plain English" writing-style
    discipline, deliberately deferred out of this change) needs a human-controlled, on/off switch for
    AI doctrine/generation behavior — something a human can enable or disable, with the change
    provably authorized and the current state provably valid, in both downstream projects and Codeos's
    own self-development. No such mechanism exists today. Without one, every feature that needs a
    toggle would either invent its own ad hoc YAML shape and validation logic, or (worse) leave the
    "is this on?" question to be answered by an LLM re-deriving a state machine from prose each time —
    the same duplication risk Codeos's single-canonical-doctrine-source principle exists to avoid, one
    layer down.
    
    ## Upgrade
    
    Ship one small, reusable, deterministic mechanism: a generic activation-file schema (documented once
    in `templates/conventions.md`), a reusable uninstantiated template
    (`templates/governed-mechanism-activation.yaml`), and a Rust resolver
    (`tools/activation-resolver/`, binary `codeos-activation-resolver`, wrapped by
    `scripts/resolve-governed-activation.sh`) that validates an activation file's current state and
    reports exactly one of three outcomes — `active` / `inactive` / `blocked` — via stable JSON result
    codes. A future feature calls the resolver instead of re-implementing state validation itself.
    
    Key design points, refined across eight review rounds during planning:
    - A **caller-supplied absence policy** (`inactive` or `blocked`) decides what a missing activation
      file means — the convention does not assume silently-inactive is always safe, since that would let
      file deletion bypass human authorization.
    - **Two governance modes** — `standalone` (no versioned artifact) and `versioned-artifact` (governs
      a companion file that must declare its own version) — selected explicitly by the caller and
      cross-checked against the file's own declared mode.
    - A disabled activation is **fully independent of its (possibly absent, possibly stale) governing
      artifact** — status alone gates whether the resolver ever opens that external file.
    - **Three ordered validation phases**: invocation validation (CLI-level, non-zero exit on caller
      misuse) → activation-file structure validation (never touches the external artifact) → a status
      branch that only now, when `enabled` + `versioned-artifact`, opens and version-checks the external
      file.
    - Path resolution is against an **explicit `--repository-root`**, never process working directory,
      with a lexical (not canonicalize-and-contain) safety rule that still allows traversal through the
      `.codeos` symlink `scripts/dba-init.sh` already creates.
    - A **simplified single transition rule** (any authorized edit to any non-identity field increments
      `state_revision` by exactly one) replaces an earlier, more complex identity/governed-state/
      provenance three-way split, with an explicit acknowledgment of what the resolver can verify from
      one snapshot versus what only `git diff`/review can confirm across a sequence.
    
    **Definition of success**: `codeos-activation-resolver` (via its wrapper) resolves a hand-specialized
    copy of the reusable template end-to-end — `ACTIVE` when correctly configured, the correct `blocked`
    code for each documented failure — with no concrete activation instance, no prompt wiring, and no
    Controlled Plain English content shipped alongside it.
    
    ## Scope
    
    **In scope**: `templates/conventions.md` (the convention's full documentation), the reusable
    uninstantiated template, the Rust resolver crate and its test suite, the thin shell wrapper, a short
    `dba-system.md` doctrine-pointer section, this brief.
    
    **Out of scope**: any concrete activation file (downstream or self-dev); any change to
    `scripts/dba-init.sh`, `CLAUDE.md`, or `prompts/codeos-self-dev.md`; any Controlled Plain English
    content (pattern file, layer split, provenance stamping — all deferred to a future consuming UPG);
    any Non-Negotiable Rule change; any new Stage ID; any new mandatory human-approval gate; any
    content-hash/digest provenance mechanism; runtime product feature flags (a different category of
    thing entirely — this governs AI doctrine/generation behavior, never application runtime behavior).
    
    ## Value
    
    Gives every future toggle-needing feature a single, already-reviewed, deterministic mechanism to
    build on, instead of each one inventing its own ad hoc validation. Removes the risk of 15+ activation
    states being re-interpreted inconsistently by different prompts. Small and fully reversible — nothing
    consumes it yet, so there is no behavioral risk from shipping it.
    
    Trade-off: this is infrastructure with no consumer yet. That risk is accepted because the next
    consumer (Controlled Plain English) is already known and the mechanism's design was driven by that
    concrete need, not built speculatively.
    
    ## Risk
    
    Low for behavior (nothing calls it yet); moderate for design durability, since a generic mechanism is
    harder to change once a real feature depends on it. Mitigated by the eight rounds of adversarial
    review already applied to the design during planning, and by keeping the resolver's contract (CLI
    flags, JSON envelope, stable codes) the single thing future callers depend on — internal
    implementation (crate structure, exact YAML library) stays free to evolve.
    
    ## Guardrail
    
    - This UPG ships the mechanism only. It must not scaffold any concrete activation file, anywhere,
      under any name.
    - `templates/governed-mechanism-activation.yaml` must remain deliberately invalid when used
      unspecialized (its placeholder `activation_id` must fail the stable-ID format), so it can never be
      accidentally deployed as a working activation.
    - The resolver's stable result codes and JSON envelope are the contract; internal implementation
      details are not.
    - Do not let this become a second governance layer parallel to `dba-system.md` — it is a mechanism a
      future doctrine change may adopt, not doctrine itself. `dba-system.md`'s new section says
      explicitly that no current doctrine rule uses it yet.
    
    ## Related
    
    - Originally proposed together with a "Controlled Plain English" writing-style discipline; narrowed
      to this generic mechanism only, at the human's explicit direction, after the combined plan grew
      too large during planning review. Controlled Plain English will be filed as its own future UPG
      once this mechanism ships.

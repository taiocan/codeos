   148	### Architectural invariants
   149	
   150	1. **No `DBA-N` carries `approved` status without an explicit human approval of that exact pinned
   151	   combination — including `DBA-1`.** The current live system was approved incrementally, over
   152	   many separate change records; that is not the same as approving "`DBA-1` — this exact
   153	   combination — as a configuration object." `DBA-1` must be (a) constructed as the
   154	   configuration-equivalent of today's live system, (b) proven semantically equivalent through the
   155	   delta inventory and compatibility sweep, (c) explicitly approved as the migration baseline, and
   156	   only then (d) activated. Filing this brief does **not** pre-approve `DBA-1`; both `DBA-1.yaml`
   157	   and `DBA-2.yaml` above are illustrative candidates only.
   158	2. **Configuration activation is atomic.** The active pointer names exactly one approved `DBA-N`.
   159	   Components are never activated individually; there is no partially-migrated state.
   160	3. **Published component versions are immutable.** A change is always a new `vN+1`. Old
   161	   configurations remain readable, so a feature's provenance is reconstructible.
   162	4. **A component split must earn its place** — independent authority, independent lifecycle, a
   163	   real reason to vary separately.
   164	5. **Configuration binding is explicit and per-feature.** Every feature must have exactly one
   165	   explicitly recorded governing `DBA-N`. Changing the globally active configuration must never
   166	   silently migrate the governing rules of work already in progress; moving in-flight work to a
   167	   different `DBA-N` requires an explicit human decision and an impact assessment — mirroring how
   168	   `UPG-0051`'s Architecture Baseline versioning already treats in-flight Stage 4 work under a
   169	   superseded baseline version. This gives real provenance (`F-0017 → DBA-1`), not just "whatever
   170	   happened to be globally active later." **Deliberately left open for the change that designs the
   171	   binding mechanism** (not frozen by this brief, and not bound to any specific CHG's Step 1):
   172	   exactly when a feature's binding is recorded — Stage 1 entry, Feature Brief
   173	   acceptance, or some other precise point — and the single canonical location that binding lives.
   174	   Avoid duplicating it across Intent, the feature registry, and the review log; every other
   175	   surface derives or references the one canonical record, never restates it.

   179	the unit whose combined coherence is reviewed and human-approved — that's sufficient. If
   180	combinations become numerous enough that this gets hard to reason about by hand, automate later;
   181	building it now would be premature infrastructure.

   161	   configurations remain readable, so a feature's provenance is reconstructible.
   162	4. **A component split must earn its place** — independent authority, independent lifecycle, a
   163	   real reason to vary separately.
   164	5. **Configuration binding is explicit and per-feature.** Every feature must have exactly one
   165	   explicitly recorded governing `DBA-N`. Changing the globally active configuration must never
   166	   silently migrate the governing rules of work already in progress; moving in-flight work to a
   167	   different `DBA-N` requires an explicit human decision and an impact assessment — mirroring how
   168	   `UPG-0051`'s Architecture Baseline versioning already treats in-flight Stage 4 work under a
   169	   superseded baseline version. This gives real provenance (`F-0017 → DBA-1`), not just "whatever
   170	   happened to be globally active later." **Deliberately left open for the change that designs the
   171	   binding mechanism** (not frozen by this brief, and not bound to any specific CHG's Step 1):
   172	   exactly when a feature's binding is recorded — Stage 1 entry, Feature Brief
   173	   acceptance, or some other precise point — and the single canonical location that binding lives.
   174	   Avoid duplicating it across Intent, the feature registry, and the review log; every other
   175	   surface derives or references the one canonical record, never restates it.

   177	**Deliberately not included yet**: no cross-component dependency declarations (e.g.

   179	the unit whose combined coherence is reviewed and human-approved — that's sufficient. If

   204	duplicated, or already-superseded rules only — any semantic removal is `INTENTIONAL-BEHAVIOR-
   205	CHANGE` instead) / `INTENTIONAL-BEHAVIOR-CHANGE` (meaning changes, **regardless of whether the
   206	rule's component also changes** — it still names a `target_owner` for the new form, and requires

   209	covers zero-semantic-loss removal). Meaning and location are two independent axes: a rule can
   210	change meaning *and* move components at once, and that combination is always
   211	`INTENTIONAL-BEHAVIOR-CHANGE`, never `MOVE`. The table above seeds that inventory; it does not
   212	substitute for it. The inventory is allowed to challenge this brief's own proposed component

    47	A naive fix — "just split the file into smaller linked Markdown fragments" — introduces a new risk

    54	## Upgrade
    55	
    56	Replace "one monolithic doctrine file" with a **versioned configuration system**: independently
    57	versioned components, assembled only through an explicitly human-approved, immutable
    58	configuration. Three distinct concepts:
    59	
    60	| Concept | Definition |
    61	|---|---|

    64	| **Active configuration** | The single `DBA-N` currently named by `dba-system.md`. |

   149	### Architectural invariants
   150	
   151	1. **No `DBA-N` carries `approved` status without an explicit human approval of that exact pinned
   152	   combination — including `DBA-1`.** The current live system was approved incrementally, over
   153	   many separate change records; that is not the same as approving "`DBA-1` — this exact
   154	   combination — as a configuration object." `DBA-1` must be (a) constructed as the
   155	   configuration-equivalent of today's live system, (b) proven semantically equivalent through the
   156	   delta inventory and compatibility sweep, (c) explicitly approved as the migration baseline, and
   157	   only then (d) activated. Filing this brief does **not** pre-approve `DBA-1`; both `DBA-1.yaml`
   158	   and `DBA-2.yaml` above are illustrative candidates only.
   159	2. **Configuration activation is atomic.** The active pointer names exactly one approved `DBA-N`.
   160	   Components are never activated individually; there is no partially-migrated state.
   161	3. **Published component versions are immutable.** A change is always a new `vN+1`. Old
   162	   configurations remain readable, so a feature's provenance is reconstructible.
   163	4. **A component split must earn its place** — independent authority, independent lifecycle, a
   164	   real reason to vary separately.
   165	5. **Configuration binding is explicit and per-feature.** Every feature must have exactly one
   166	   explicitly recorded governing `DBA-N`. Changing the globally active configuration must never
   167	   silently migrate the governing rules of work already in progress; moving in-flight work to a
   168	   different `DBA-N` requires an explicit human decision and an impact assessment — mirroring how
   169	   `UPG-0051`'s Architecture Baseline versioning already treats in-flight Stage 4 work under a
   170	   superseded baseline version. This gives real provenance (`F-0017 → DBA-1`), not just "whatever
   171	   happened to be globally active later." **Deliberately left open for the change that designs the
   172	   binding mechanism** (not frozen by this brief, and not bound to any specific CHG's Step 1):
   173	   exactly when a feature's binding is recorded — Stage 1 entry, Feature Brief
   174	   acceptance, or some other precise point — and the single canonical location that binding lives.
   175	   Avoid duplicating it across Intent, the feature registry, and the review log; every other
   176	   surface derives or references the one canonical record, never restates it.
   177	
   178	**Deliberately not included yet**: no cross-component dependency declarations (e.g.
   179	`review/v3 requires doctrine >= v4`), no compatibility solver. A `DBA-N` configuration is already
   180	the unit whose combined coherence is reviewed and human-approved — that's sufficient. If
   181	combinations become numerous enough that this gets hard to reason about by hand, automate later;
   182	building it now would be premature infrastructure.

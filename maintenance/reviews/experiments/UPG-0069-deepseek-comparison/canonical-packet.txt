    # Reviewer Tool Contract — v4
    
    ## Supported Interface
    
    Use `.codeos/toolkit/dba/04-tools/reviewer/codeos-review.sh` downstream and
    `dba/04-tools/reviewer/codeos-review.sh` for Codeos self-development. The wrapper resolves the
    compiled reviewer binary relative to the toolkit and delegates these supported operations:
    
    | Operation | External purpose |
    |---|---|
    | `review` | Build review evidence, invoke Codex, and record the result |
    | `plan` | Preview the same validated evidence selection without invoking Codex or writing records, and optionally export the packet |
    | `decision` | Append the human decision associated with an automated review |
    | `diagnose` | Report resolved reviewer configuration |
    | `inspect-architecture-scopes` | Validate and report Architecture Scope metadata without invoking a reviewer |
    
    Use `codeos-review.sh <operation> --help` for exact arguments and options. At a review point governed
    by the selected review policy, the usual invocation is:
    
    ```text
    .codeos/toolkit/dba/04-tools/reviewer/codeos-review.sh review <feature_id> <workflow-or-stage> [artifacts and options]
    ```
    
    Use Stage ID `3` for the complete Specification Package. The Stage-3 packet evaluates Intent,
    Contract, Event Schema, and their consistency.
    
    Support-workflow reviews use `framing`, `decomposition`, or `intake`. The two support-workflow
    decision boundaries use `charter` for Solution Charter approval and `architecture` for the
    Architecture Synthesis boundary; `architecture` covers both creating a scope and revising an
    approved one, because a material change repeats the same boundary. Numeric Stage IDs remain
    `1` through `9`. Historical records keep the identifiers recorded when they were created.
    
    Omitting `--base` selects full-file evidence. `--base <ref>` resolves the ref to a commit and selects
    changes since that commit. `plan` and `review` apply the same validation, evidence selection, and
    packet construction for equivalent inputs; `plan` stops before invocation and durable writes.
    Artifact and hash-only paths must resolve to regular files inside the project repository. A symlink
    whose target remains inside the repository is valid; a resolved target outside it is rejected.
    
    `plan --emit-packet <file>` writes the packet `review` would send for the same inputs. There is one
    packet construction path; the exported bytes are the reviewed bytes. Exporting into the reviewed
    working tree is permitted but warned about, because the exported file then becomes evidence in the
    next packet.
    
    `review --fresh` starts a new Codex session. Without it, the reviewer may resume saved session state.
    `review --scratch` keeps review records in ignored operational state. Session storage, Codex command
    flags, JSONL event shapes, process handling, and internal module/type structure are implementation
    details rather than compatibility guarantees.
    
    ## External Assessment
    
    `review --assessment <file>` records an external assessment: findings produced by a model Codeos did
    not invoke, supplied by a human. `--reviewer-label <label>` names that model as descriptive metadata
    only; Codeos neither invoked nor verified it and cannot confirm the text originated there.
    
    This path invokes no reviewer. It applies the same evidence selection, packet construction, response
    parsing, and fail-closed schema validation as `review`. An unreadable or empty assessment file fails
    before any durable write.
    
    An external assessment is not a review. Its record states `source: external`, is sequenced as
    `EXT__<feature>__<stage>__A<N>` rather than `REV__…__R<N>`, and does not advance the review round —
    the next Codex-backed review of the same feature and stage still claims the round it would have
    claimed. Process measurements that describe a run Codeos performed (reasoning effort, reconnects,
    wall time) are absent rather than defaulted. Whether an external assessment can satisfy a governed
    review obligation is owned by the selected review policy, not by this tool.
    
    Model transport lives outside this tool. `codeos-review-deepseek.sh` is one adapter: packet in, raw
    assessment out. It holds no reviewer authority and writes no reviewer record.
    
    ## Configuration
    
    Codex is the only reviewer this tool invokes. Optional reasoning effort resolves in this order:
    `CODEOS_REASONING_EFFORT`, `.codeos/05-review/reviewer.toml`, then the compiled `high` default.
    The configuration file accepts only `reasoning_effort`; malformed configuration and unknown keys,
    including retired provider keys, fail before Codex invocation. There is no provider selection: an
    assessment from any other model enters through `review --assessment` rather than through
    configuration.
    
    ## Automated Review Records
    
    The reviewer tool is the single authoritative owner of automated review records. A completed
    Codex-backed `review` preserves the reviewed packet and assessment and appends the review result
    to the global review log selected for the current project context. `decision` appends its associated
    human decision; existing entries and assessments are not rewritten.
    
    The append-only property, the connection between a decision and its reviewed evidence, and visible
    handling of incomplete evidence are external integrity guarantees. Exact record structures, storage
    subpaths, parsing, sequencing, and algorithms belong to the Rust implementation and tests unless
    this contract explicitly makes them compatibility guarantees. The canonical downstream record root
    `.codeos/05-review/reviews/` is owned by the Downstream Project Layout Contract.
    
    An empty review packet fails before Codex invocation. Malformed final assessment output is recorded as
    unclassified rather than silently accepted. `decision` refuses an approval token when required
    review provenance is unreadable or evidence coverage is critical or empty unless the human supplies
    an explicit override rationale. Reviewer concern levels alone never approve, refuse, or complete a
    DBA boundary.
    
    ## Authority Boundary
    
    The reviewer is read-only and advisory. Its records provide evidence; they do not own feature
    lifecycle state or approval. A human owns the decision required by the applicable doctrine boundary,
    including any explicit override recorded through `decision`.
    
    `inspect-architecture-scopes` is deterministic and read-only. It reports membership and recorded
    approval state but has no reviewer, verdict, approval, or architecture-decision authority.

    # Review Policy — v2
    
    ## Default Review Timing
    
    Advisory review runs by default immediately before each decision boundary required by the selected
    doctrine and before a conditional architecture decision required by the selected architecture
    policy. Review does not create a decision boundary of its own.
    
    ## Reviewer Independence
    
    The reviewer is independent, read-only,
    and non-gatekeeping — its verdict (NO OBJECTION / CHANGES ADVISED / DO NOT ADVANCE) informs the
    owner of the applicable boundary but never auto-blocks or completes that boundary.
    
    ## Review Round Limit
    
    **Round budget.** Round 1 runs before the applicable boundary. Rounds 2-3 are allowed for fixes or material
    deltas raised by the previous round. After 3 rounds, stop and require a human decision rather
    than continuing to iterate automatically.
    
    ## Solution Framing Review
    
    **Solution Framing is reviewed conditionally, not unconditionally.** Framing stays optional and
    non-authoritative — running it is never required, and its output is never approved solution truth
    or architecture. If a proposal is promoted into a governed artifact, the claim is reviewed at the
    next applicable review point. Framing whose output nobody acts on is simply never reviewed.
    
    ## External Assessment
    
    An external assessment supplies findings from a model Codeos did not invoke. External findings are
    actionable. No findings does not prove that no problem exists — the absence of findings from a model
    whose recall is unmeasured is not evidence of absence.
    
    An external assessment therefore never satisfies a required review round, whatever verdict it
    reports. When a required review cannot run, an external assessment may still provide findings, but
    progression requires the Review Waiver below:
    
    ```text
    reviewer unavailable -> external assessment for findings -> fix findings -> Review Waiver -> human gate
    ```
    
    Its record is kept distinct from a review record and does not advance the round count.
    
    ## Review Waiver
    
    **Review Waiver.** If reviewer tooling is unavailable or not configured for this project, the
    human records an explicit waiver with a reason and may continue — skipping the review silently is
    not allowed, and neither is blocking the whole project over missing reviewer setup.
    
    Record it as a plain entry in that feature's review log: "Review waiver: reviewer not
    configured for this project; proceeding without advisory review at `<stage>`. Reason:
    `<text>`."
    
    ## Verification-Only Evidence
    
    **Verification round-trip.** When a reviewer's assessment names a `HIGHEST-IMPACT
    UNCERTAINTY` that is mechanically checkable — a specific file, command, or repository state
    that can directly confirm or refute it — the acting agent may run
    `.codeos/toolkit/dba/03-prompts/review/verify-only.md`'s read-only verification pass targeting exactly
    that uncertainty, then attach its Verification-Only Report as evidence for the next review
    round. This is optional and
    judged by the acting agent, not automatic or mandatory — not every uncertainty is
    mechanically checkable, and declining to run it is always a valid choice. Verification
    remains strictly read-only (see `verify-only.md`'s No-Edit Rule); it produces evidence for
    the human's decision, it does not replace it. A verification pass is not itself a review
    round and does not consume the round budget above — only the review round it feeds into does.
    
    ## Supplementary Independent Review
    
    **Relationship to the Reviewer Activation Package**
    (`.codeos/toolkit/dba/03-prompts/review/pipeline-reviewer.md`).
    That prompt remains available as an **optional, supplementary** independent critical-assessor
    pass — a human can paste it into a separate reviewer session for a second opinion that is
    free to challenge the artifact, the feature, or DBA itself, not just check it against
    acceptance criteria. It does not replace the default review above.
    
    ## Automated Review Record Ownership
    
    The reviewer tool is the single authoritative owner of automated review records. Its supported
    review and decision operations record the automated assessment and associated human decision
    without requiring Claude or the project to maintain a synchronized per-feature review log.
    
    This policy defines record ownership, not storage topology. Feature-specific automated review
    history may be obtained by filtering tool-owned records using feature, change, or review identifiers
    already present in those records. Do not introduce a new index, identifier, or copied feature log
    merely to make filtering easier. If reliable filtering is not currently possible, leave it that way
    until a demonstrated need justifies a change.
    
    The reviewer tool's decision operation records a human decision associated with an automated
    review; it does not acquire approval authority. The applicable doctrine boundary remains the owner
    of approval.
    
    ## Other Human Review Decisions
    
    A human decision not produced through the automated reviewer is recorded at the governing artifact
    or approval boundary that naturally owns it. Do not create an automated-review-shaped record or a
    parallel synchronization surface for it.
    
    ## Review-Process Measurement
    
    `dba/05-guidance/templates/review-file.md` is an optional, non-authoritative template for evaluating
    review effectiveness and cost. It may reference tool-owned records by their existing identifiers,
    but it must not copy or independently maintain their findings, verdicts, approval state, lifecycle
    state, or history. Measurements that can be calculated from tool-owned records are derived from
    those records rather than maintained as a second source of facts.

    #!/usr/bin/env bash
    # codeos-review-deepseek.sh — transport only. Sends a canonical reviewer packet to DeepSeek and
    # writes the raw reply back out. It parses nothing, decides nothing, and writes no reviewer record.
    #
    # This is the model-transport half of the external-assessment path:
    #
    #   codeos-review.sh plan <feature> <stage> --emit-packet PACKET <artifacts...>
    #   codeos-review-deepseek.sh PACKET ASSESSMENT
    #   codeos-review.sh review <feature> <stage> --assessment ASSESSMENT \
    #       --reviewer-label deepseek-v4-flash <artifacts...>
    #
    # The packet already carries the reviewer task prompt, so it is sent as the user message and no
    # system message is added: the packet is what a Codex-backed review would have received, verbatim.
    #
    # The result is an EXTERNAL ASSESSMENT. It supplies advisory findings and never satisfies a required
    # review round — see dba/02-policies/review/v2.md. DeepSeek-specific knowledge stops in this file;
    # the reviewer engine holds no credentials and no provider configuration.
    #
    # Usage:
    #   codeos-review-deepseek.sh <packet-file> <assessment-file>
    #
    # Environment:
    #   DEEPSEEK_API_KEY  required. Read only into the HTTP Authorization header via a curl config on
    #                     stdin — never in argv, the request body, or any written file.
    #   CODEOS_DEEPSEEK_MODEL       optional, default "deepseek-v4-flash".
    #   CODEOS_DEEPSEEK_URL         optional, default "https://api.deepseek.com/chat/completions".
    #   CODEOS_DEEPSEEK_MAX_TOKENS  optional, default 32768. The only other supported value is 65536,
    #                               for one explicit retry after finish_reason=length. A retry is a new
    #                               invocation so both attempts remain visible and count toward cost.
    #
    # Exit codes:
    #   0  success — assessment written
    #   2  missing dependency (curl or jq not found on PATH)
    #   3  usage error, or an unsupported max-tokens bound (checked before any network call)
    #   6  DEEPSEEK_API_KEY unset or empty — refuse before any network call
    #   7  the packet file does not exist or is empty
    #   8  DeepSeek API / transport error, or a response that did not terminate normally
    set -euo pipefail
    
    err() { echo "error: $*" >&2; }
    
    if [[ $# -ne 2 ]]; then
      err "usage: codeos-review-deepseek.sh <packet-file> <assessment-file>"
      exit 3
    fi
    PACKET="$1"
    OUT="$2"
    
    for dep in curl jq; do
      command -v "${dep}" >/dev/null 2>&1 || { err "required dependency '${dep}' not found on PATH"; exit 2; }
    done
    
    [[ -s "${PACKET}" ]] || { err "packet file is missing or empty: ${PACKET}"; exit 7; }
    
    MODEL="${CODEOS_DEEPSEEK_MODEL:-deepseek-v4-flash}"
    DS_URL="${CODEOS_DEEPSEEK_URL:-https://api.deepseek.com/chat/completions}"
    MAX_TOKENS="${CODEOS_DEEPSEEK_MAX_TOKENS:-32768}"
    if [[ "${MAX_TOKENS}" != "32768" && "${MAX_TOKENS}" != "65536" ]]; then
      err "CODEOS_DEEPSEEK_MAX_TOKENS must be 32768 or 65536; got '${MAX_TOKENS}'"
      exit 3
    fi
    
    if [[ -z "${DEEPSEEK_API_KEY:-}" ]]; then
      err "DEEPSEEK_API_KEY is unset or empty; refusing to run (no network call made)."
      exit 6
    fi
    
    OUT_DIR="$(dirname "${OUT}")"
    mkdir -p "${OUT_DIR}"
    RESP_FILE="${OUT}.response.json"
    TOKENS_FILE="${OUT}.tokens.txt"
    
    # --rawfile, not --arg: a single argv element is capped at 128 KiB on Linux (MAX_ARG_STRLEN) and a
    # realistic reviewer packet exceeds that. Reading from the file avoids argv entirely.
    REQ_BODY="${OUT}.request.json"
    jq -n --arg model "${MODEL}" \
          --argjson max_tokens "${MAX_TOKENS}" \
          --rawfile packet "${PACKET}" \
      '{model:$model,
        messages:[{role:"user",content:$packet}],
        thinking:{type:"enabled"},
        reasoning_effort:"high",
        max_tokens:$max_tokens,
        stream:false}' > "${REQ_BODY}"
    
    HTTP_CODE="$(
      printf 'header = "Authorization: Bearer %s"\n' "${DEEPSEEK_API_KEY}" \
        | curl -sS -K - \
            -H 'Content-Type: application/json' \
            -X POST "${DS_URL}" \
            --data-binary @"${REQ_BODY}" \
            -o "${RESP_FILE}" \
            -w '%{http_code}' \
        || true
    )"
    if [[ ! "${HTTP_CODE}" =~ ^2[0-9][0-9]$ ]]; then
      err "DeepSeek API call failed (http_code=${HTTP_CODE:-none}); response saved to ${RESP_FILE}"
      exit 8
    fi
    
    # Accounting is recorded before the reply is interpreted, so a truncated or otherwise non-normal
    # response stays attributable and costed without persisting the model's reasoning content.
    PT="$(jq -r '.usage.prompt_tokens // "?"' "${RESP_FILE}")"
    CT="$(jq -r '.usage.completion_tokens // "?"' "${RESP_FILE}")"
    TT="$(jq -r '.usage.total_tokens // "?"' "${RESP_FILE}")"
    PCH="$(jq -r '.usage.prompt_cache_hit_tokens // "?"' "${RESP_FILE}")"
    PCM="$(jq -r '.usage.prompt_cache_miss_tokens // "?"' "${RESP_FILE}")"
    RT="$(jq -r '.usage.completion_tokens_details.reasoning_tokens // "?"' "${RESP_FILE}")"
    RETURNED_MODEL="$(jq -r '.model // "?"' "${RESP_FILE}")"
    FINISH_REASON="$(jq -r '.choices[0].finish_reason // "?"' "${RESP_FILE}")"
    printf 'prompt_tokens=%s completion_tokens=%s total_tokens=%s prompt_cache_hit_tokens=%s prompt_cache_miss_tokens=%s reasoning_tokens=%s requested_model=%s returned_model=%s finish_reason=%s max_tokens=%s\n' \
      "${PT}" "${CT}" "${TT}" "${PCH}" "${PCM}" "${RT}" "${MODEL}" "${RETURNED_MODEL}" \
      "${FINISH_REASON}" "${MAX_TOKENS}" > "${TOKENS_FILE}"
    
    # Only a natural stop is a complete assessment. A truncated reply is preserved and accounted, but is
    # never written to the assessment path where it would be imported as if it were whole.
    if [[ "${FINISH_REASON}" != "stop" ]]; then
      err "response did not terminate normally (finish_reason=${FINISH_REASON}); see ${RESP_FILE}"
      if [[ "${FINISH_REASON}" == "length" && "${MAX_TOKENS}" == "32768" ]]; then
        err "       retry once with CODEOS_DEEPSEEK_MAX_TOKENS=65536"
      fi
      exit 8
    fi
    
    # -j, not -r: the reply is written byte for byte rather than gaining a newline jq would append.
    # A single trailing newline is then guaranteed, so the file is a well-formed text file either way.
    jq -j '.choices[0].message.content // empty' "${RESP_FILE}" > "${OUT}"
    if [[ -s "${OUT}" && -n "$(tail -c1 "${OUT}")" ]]; then printf '\n' >> "${OUT}"; fi
    if [[ ! -s "${OUT}" ]]; then
      err "model returned an empty reply; see ${RESP_FILE}"
      rm -f "${OUT}"
      exit 8
    fi
    
    echo "external assessment written: ${OUT}"
    echo "  tokens: prompt=${PT} completion=${CT} reasoning=${RT} total=${TT}   model=${RETURNED_MODEL}"
    echo "  NOTE: advisory only — import with 'codeos-review.sh review ... --assessment ${OUT}'."
    echo "        An external assessment never satisfies a required review round."

+## External Assessment
+
+An external assessment supplies findings from a model Codeos did not invoke. External findings are
+actionable. No findings does not prove that no problem exists — the absence of findings from a model
+whose recall is unmeasured is not evidence of absence.

+progression requires the Review Waiver below:
+

+reviewer unavailable -> external assessment for findings -> fix findings -> Review Waiver -> human gate

/// How the reviewed text was obtained.
///
/// This is a record of provenance, not a provider abstraction: there is no dispatch, no trait, and
/// no configuration behind it. Codeos either invoked Codex itself, or a human handed it text that
/// some other model produced. The two cases carry genuinely different fields — a session id and a
/// reconnect count only exist for a process this tool ran — so they are kept apart rather than
/// filled with placeholder values that would read as if Codeos had verified something it did not.
pub enum RunSource {
    /// Codeos invoked the Codex CLI. This is the only source that counts as a review round.
    Codex {
        session_id: String,
        reconnect_count: u32,
        effort: String,
    },
    /// A human supplied an assessment produced elsewhere. `label` is descriptive metadata only:
    /// Codeos neither invoked nor verified the named model, and cannot confirm the text came from
    /// it. Advisory evidence — never a review round.
    External { label: Option<String> },
}

/// One reviewer run: the raw reply text plus where it came from.
pub struct ReviewerRun {
    pub text: String,
    pub elapsed_ms: u64,
    pub source: RunSource,
}

impl ReviewerRun {
    pub fn is_external(&self) -> bool {
        matches!(self.source, RunSource::External { .. })
    }

    /// The `reviewer:` value written into records. For an external assessment the phrasing states
    /// the limit of what Codeos knows, so no reader can mistake the label for verification.
    pub fn reviewer_field(&self) -> String {
        match &self.source {
            RunSource::Codex { session_id, .. } => format!("codex (session {session_id})"),
            RunSource::External { label } => match label {
                Some(label) => format!(
                    "external assessment ({label}, as supplied — not invoked or verified by Codeos)"
                ),
                None => {
                    "external assessment (model unstated — not invoked or verified by Codeos)"
                        .to_string()
                }
            },
        }
    }
}

## 1. The current support layer is more fragmented than necessary

The first three workflows are conceptually very close:

```text
00a-solution-discovery
        ↓
00-full-solution-concept
        ↓
00-charter
```

They all deal with the same solution-level questions:

> **Problem → Vision → Outcomes → Scope → Constraints**

The real distinction is not their subject matter. It is **authority**:

* discovery/concept = exploration;
* Charter = governed truth.

That distinction should remain.

I would therefore reduce these **three conceptual workflows to two**.

### A. Solution Framing — non-authoritative

One workflow answers all five questions:

```text
Problem
Vision
Outcomes
Scope
Constraints
```

Its purpose is:

> Understand and frame the solution before governing it.

It can replace both:

```text
00a-solution-discovery.md
00-full-solution-concept.md
```

The output can still be a `full-solution-concept.md` if that artifact is useful.

There is little value in having one workflow discover the problem and another independently synthesize Problem + Vision + Outcomes + Scope again.

### B. Solution Charter — authoritative

Keep this separate and deliberately small.

Its purpose becomes:

> Review the proposed solution framing and approve only the minimum solution-level authority needed by downstream work.

The Charter contains the governed subset:

```text
Problem
Vision
Outcomes
Scope / Boundary
System Constraints
```

The important difference becomes extremely clear:

```text
Solution Framing
    exploratory
    can hypothesize
    can change freely
        ↓
Solution Charter
    governed
    concise
    approved
        ↓
Feature Intents
```

This is simpler than three workflows **without weakening the authority boundary**.

---

# 2. I would not combine framing and Charter approval into one workflow

It is technically possible to create one large workflow:

```text
Discover → Frame → Approve
```

but I don't recommend it.

The same prompt would then be responsible for both:

> “Explore freely”

and:

> “Create governed truth.”

That makes the authority boundary harder to understand and easier for an agent to cross accidentally.

So I think **two parts is the sweet spot**:

> **Solution Framing + Solution Charter**

not three, and not one.

---

# 3. The support workflow set can therefore become much simpler

Conceptually, I would aim for this:

| Support workflow             | Purpose                                           |
| ---------------------------- | ------------------------------------------------- |
| **Solution Framing**         | Problem, Vision, Outcomes, Scope, Constraints     |
| **Solution Charter**         | Approve solution-level authority                  |
| **Feature Decomposition**    | Turn solution scope into candidate features       |
| **Existing-Codebase Intake** | Understand an existing system before applying DBA |
| **Architecture Synthesis**   | Resolve cross-feature structural decisions        |
| **Session Orientation**      | Determine what work should happen now             |
| **Session Handoff**          | Preserve state for the next session               |

That gives **7 support workflows instead of 8**, but more importantly the first part now has a much clearer model.

I would not force further consolidation. For example:

* onboarding solves a different entry condition;
* architecture synthesis has different authority and timing;
* session start/end have operational purposes rather than engineering reasoning purposes.

Combining those would save filenames but increase prompt branching.

---

# 4. I would also question whether `Feature Decomposition` should be positioned in a linear A sequence

Your current proposed sequence implies:

```text
A0 Problem Discovery
A1 Full Solution Concept
A2 Charter
A3 Feature Decomposition
A4 Existing Codebase Intake
A5 Architecture
A6 Session Orientation
A7 Session Handoff
```

But this is not really one sequence.

For example:

```text
Existing-Codebase Intake
```

can happen before Solution Framing.

And:

```text
Session Orientation
```

can happen before virtually anything.

Architecture Synthesis happens later, after relevant feature specifications exist.

So `A0–A7` creates a conceptual order that does not actually exist, even if documentation says it is “inventory order only.”

That is a smell.

If you have to explain:

> “The consecutive numbering looks like sequence, but it is not sequence”

then the namespace is not helping enough.

---

# 5. Therefore I would drop the “gap-free A namespace” requirement

This proposed invariant is unnecessary:

> support identifiers are gap-free from A0.

It governs cosmetics rather than engineering behavior.

Suppose later you remove one support workflow. Why should this:

```text
A0
A1
A3
A4
```

be invalid?

Nothing in software correctness depends on that.

Likewise, adding a workflow shouldn't require renaming everything after it merely to preserve sequence.

So I would **not create a mechanical contract around consecutive support numbering**.

Reserve mechanical checks for properties that protect real semantics:

```text
01–09 correspond exactly to governed Stage IDs
every referenced prompt exists
every doctrine adapter resolves to exactly one owner
support prompts cannot masquerade as Stage IDs
```

Those are valuable invariants.

“Gap-free A numbers” is not.

---

# 6. Consider avoiding numeric support IDs completely

If you eventually rename them, I think this is actually cleaner:

```text
support-solution-framing.md
support-solution-charter.md
support-feature-decomposition.md
support-codebase-intake.md
support-architecture-synthesis.md
support-session-start.md
support-session-end.md
```

versus:

```text
A0-
A1-
A2-
...
```

Why?

Because your most important discovered fact is:

> **Numbers have semantic meaning in DBA because 01–09 are Stage IDs.**

The safest solution is therefore not to create **another numeric-looking namespace**.

You get a very obvious distinction:

```text
01-intent.md
02-contract.md
03-event-schema.md
04-implement.md
...
09-refine.md

support-solution-framing.md
support-solution-charter.md
support-feature-decomposition.md
support-architecture-synthesis.md
...
```

Nobody has to learn what `A4` means.

The filename says what it is.

---

# 7. But I would still not rename them now

This is the most important practical recommendation.

You have already discovered that filenames are executable dependencies.

Therefore I would separate two questions:

### Semantic improvement

Worth doing:

```text
merge Discovery + Full-Solution-Concept workflow semantics
clarify Solution Framing → Charter
simplify responsibility boundaries
```

### Filename cleanup

Currently optional and coupled.

So do not make the semantic improvement dependent on:

```text
00a → A0
00 → A1
00-charter → A2
...
```

You could first simplify the actual workflow responsibilities while retaining existing filenames.

For example:

```text
00a-solution-discovery.md
```

could become the single **Solution Framing** workflow.

Then retire `00-full-solution-concept.md` if its workflow responsibility has been absorbed.

`00-charter.md` remains the governed step.

That produces actual simplification:

```text
BEFORE

Discovery
  ↓
Full-Solution Concept
  ↓
Charter


AFTER

Solution Framing
  ↓
Charter
```

That is much more valuable than changing eight prefixes.

# Recommended low-complexity target

I would aim for this conceptual model:

```text
                SOLUTION LEVEL

        Solution Framing
 Problem · Vision · Outcomes
   Scope · Constraints
        [non-authoritative]
               │
               ↓
        Solution Charter
       [governed authority]
               │
               ↓
      Feature Decomposition
               │
               ↓
        DBA Stages 1–3
               │
               ↓
     Architecture Synthesis
          [when needed]
               │
               ↓
        DBA Stages 4–9
```

With side-entry utilities:

```text
Existing-Codebase Intake ──→ appropriate entry point

Session Orientation ───────→ appropriate workflow/stage

Session Handoff ←────────── current work state
```

That is more truthful than forcing all support workflows into A0–A7.

## What I would change in the current proposal

I would reduce the rename initiative to these decisions:

**Keep**

> `01–09` are reserved governed Stage IDs.

**Add**

> Support workflows are not stages and MUST NOT use filenames that imply Stage identity.

**Simplify**

> Merge Problem Discovery and Full-Solution-Concept workflow responsibility into one **Solution Framing** workflow covering Problem, Vision, Outcomes, Scope, and Constraints.

**Keep separate**

> Solution Charter because it introduces governed authority.

**Remove**

> A0–A7 consecutive ordering as a governed invariant.

**Remove**

> gap-free support-prefix verification.

**Defer**

> actual filename renaming until filename/path coupling has an independent reason to be removed.

## Bottom line

I think you have uncovered a more important simplification than the original renaming task.

The best structure is **not**:

```text
8 better-named support workflows
```

It is closer to:

```text
2 solution-definition workflows
    Solution Framing
    Solution Charter

+ a few genuinely distinct support workflows
    Feature Decomposition
    Codebase Intake
    Architecture Synthesis
    Session Orientation
    Session Handoff

+ 9 governed DBA stages
```

And the key simplification is:

> **Combine Problem, Vision, Outcomes, Scope, and Constraints into one Solution Framing workflow, but keep Charter approval separate because exploration and authority are fundamentally different responsibilities.**

I would optimize for that semantic simplification first and treat namespace cleanup as secondary.

Yes. There is a fairly universal structure that works for software and, with small changes, for almost any engineered solution.

The key is to move through **four levels of thinking**:

**Why → What → How → Proof**

and within those levels move from **large decisions to small decisions**.

A strong universal sequence is:

> **Problem → Vision → Outcomes → Scope → Requirements → Architecture → Design → Detailed Specification → Build → Verify → Operate → Learn**

I would use the following structure.

| #  | Component                  | Simple question it answers                                 | Main output                                |
| -- | -------------------------- | ---------------------------------------------------------- | ------------------------------------------ |
| 1  | **Problem**                | What problem exists, and for whom?                         | Problem statement                          |
| 2  | **Vision**                 | What should the better future look like?                   | Solution vision                            |
| 3  | **Outcomes**               | What must improve for this to be successful?               | Goals + success measures                   |
| 4  | **Scope & Constraints**    | What are we solving, not solving, and what limits us?      | Scope, boundaries, constraints             |
| 5  | **Requirements**           | What must the solution do or guarantee?                    | Functional + quality requirements          |
| 6  | **Architecture**           | What major parts are needed and how do they work together? | System structure                           |
| 7  | **Design**                 | How should each major part work?                           | Component/module design                    |
| 8  | **Detailed Specification** | What exactly must be built?                                | Interfaces, rules, states, data, behaviors |
| 9  | **Implementation**         | How do we turn the specification into a working solution?  | Working system                             |
| 10 | **Verification**           | Did we build the required solution correctly?              | Tests + evidence                           |
| 11 | **Operation**              | Does it work in the real environment?                      | Running solution + observations            |
| 12 | **Learning & Evolution**   | What should change based on reality?                       | Improvements / next iteration              |

The most important thing is what each level is **allowed to decide**.

### 1. Problem — understand reality before proposing a solution

Start with:

> **What is wrong, difficult, expensive, slow, risky, or missing today?**

Describe:

* affected users or stakeholders,
* current situation,
* pain or opportunity,
* causes where known,
* consequences.

Do **not** start with technology.

Bad:

> We need an AI-powered map application.

Better:

> Land researchers need to identify relevant plots quickly. Current tools require several searches and manual cross-checking.

---

### 2. Vision — describe the desired future

Now ask:

> **What should the user's world look like if we solve the problem well?**

For example:

> A user can open one application, select search criteria and immediately see matching land plots on an interactive map.

Vision should be understandable without knowing implementation details.

This is the **big-picture solution concept**, not architecture yet.

---

### 3. Outcomes — define what success means

Ask:

> **What measurable result must the solution create?**

Examples:

* matching plots appear within 500 ms after a filter change,
* users can identify a relevant plot without changing screens,
* 95% of searches require no manual database lookup,
* information shown for a selected plot is sufficient for the next user decision.

This step prevents a project from confusing **features** with **value**.

A feature is:

> dynamic map filtering.

An outcome is:

> users find relevant plots quickly.

---

### 4. Scope and constraints — establish the boundary

Ask:

> **What belongs inside this solution? What does not? What limits our choices?**

Typical constraints include:

* budget,
* time,
* existing systems,
* regulation,
* security,
* expected scale,
* required technologies,
* available team skills.

This produces the system boundary.

For example:

```text
IN SCOPE
Search plots
Display plots on map
Show key plot information

OUT OF SCOPE
Property purchasing
Payment processing
Land valuation
```

This small step prevents enormous amounts of accidental complexity.

---

# Then move from WHY into WHAT

### 5. Requirements — define required behaviour and qualities

Ask:

> **What must the solution do?**

There are two major types.

**Functional requirements**

What must happen?

> When the user changes a search criterion, the system shall update the plots displayed on the map.

**Quality requirements**

How well must it happen?

> The updated map should normally appear within 500 ms.

Typical quality concerns include:

* performance,
* availability,
* security,
* usability,
* maintainability,
* reliability,
* scalability.

At this level, avoid specifying internal implementation unless it is genuinely required.

---

# Then move from WHAT into HOW

### 6. Architecture — divide the solution into major responsibilities

Architecture asks:

> **What are the major parts of the solution, what responsibility does each have, and how do they interact?**

A highly generic software structure might be:

```text
User
  ↓
Presentation
  ↓
Application
  ↓
Domain
  ↓
Data / External Systems
```

Or at system level:

```text
Client
  ↓
Application Service
  ↓
Domain Logic
  ↓
Data Access
  ↓
Database / External Services
```

Architecture answers questions such as:

* Where does each responsibility belong?
* Which components communicate?
* Where does data live?
* Which boundaries must remain stable?
* Which qualities drive the structure?
* Where can change happen independently?

Architecture should normally **not** specify every class, function, database column, or algorithm.

Its purpose is to establish **structural decisions that are expensive to change later**.

---

### 7. Design — define how each architectural part works

Now zoom in.

Architecture may say:

> Search Service is responsible for finding plots that satisfy user criteria.

Design explains:

```text
Search Service
 ├─ receives normalized search criteria
 ├─ validates criteria
 ├─ converts criteria into a spatial query
 ├─ queries Plot Repository
 └─ returns lightweight PlotSummary objects
```

The distinction is useful:

> **Architecture = system decomposition.**

> **Design = internal solution for each part.**

---

### 8. Detailed specification — remove ambiguity before implementation

Now ask:

> **What exactly must happen?**

This is the smallest useful level before code.

Specify things such as:

**Interfaces**

```text
GET /plots
```

**Inputs**

```text
min_area
max_area
municipality
land_use
map_bounds
```

**Outputs**

```text
plot_id
geometry
area
category
```

**Business rules**

```text
A plot matches only when all active filters are satisfied.
```

**States**

```text
idle
loading
loaded
error
```

**Events**

```text
SearchCriteriaChanged
PlotSearchRequested
PlotSearchCompleted
PlotSelected
```

**Failure behaviour**

```text
If the search service is unavailable,
the existing map remains visible
and the user sees a search failure message.
```

At this level an implementer should need to make relatively few **product decisions**.

They still retain freedom over normal internal coding choices.

---

# Then move from HOW into REALITY

### 9. Implementation

Now build it.

The important principle is:

> Implementation should mainly resolve **implementation decisions**, not rediscover product requirements or architecture.

If programmers repeatedly have to answer questions such as:

> "What should happen if X occurs?"

then the specification is probably incomplete.

If they repeatedly ask:

> "Which component should own this?"

then the architecture or design is probably incomplete.

---

### 10. Verification — prove that the intended solution was built

There are actually two questions:

> **Did we build it correctly?**

and

> **Did we build the correct thing?**

These are different.

Verification can trace directly backwards:

```text
Problem
  ↓
Outcome
  ↓
Requirement
  ↓
Architecture / Design
  ↓
Implementation
  ↓
Test / Evidence
```

For example:

```text
Requirement
Map updates after filter change

        ↓

Implementation
search → query → response → map update

        ↓

Evidence
integration test proves the behaviour
```

That traceability is one of the strongest mechanisms for producing reliable systems.

---

### 11. Operation — confront the design with reality

Once running, ask:

> **Does the system behave correctly in its real environment?**

Now you can observe things specifications cannot completely predict:

* actual latency,
* user behaviour,
* unexpected failures,
* load patterns,
* usability problems,
* data-quality problems.

This is why implementation is not really the end.

---

### 12. Learning and evolution

Finally ask:

> **What did reality teach us?**

The result may modify:

* the problem understanding,
* objectives,
* requirements,
* architecture,
* design,
* implementation.

So the complete model is not really a straight line.

It is:

```text
PROBLEM
   ↓
VISION
   ↓
OUTCOMES
   ↓
SCOPE
   ↓
REQUIREMENTS
   ↓
ARCHITECTURE
   ↓
DESIGN
   ↓
SPECIFICATION
   ↓
IMPLEMENTATION
   ↓
VERIFICATION
   ↓
OPERATION
   ↓
LEARNING
   └──────────────────────↺
```

That feedback loop is critical.

---

## I would simplify the entire structure into six layers

If you want something **very universal and easy to remember**, I think this is even stronger:

```text
1. PURPOSE
   Why should anything change?

2. OUTCOME
   What should become better?

3. REQUIREMENTS
   What must the solution do?

4. STRUCTURE
   What major parts make the solution work?

5. BEHAVIOUR
   How exactly must those parts behave?

6. EVIDENCE
   How do we know the solution works?
```

And beneath these sits **Implementation**, which realizes them:

```text
WHY
│
├─ Purpose
├─ Outcomes
│
WHAT
│
├─ Scope
├─ Requirements
│
HOW
│
├─ Architecture
├─ Design
├─ Detailed Specification
│
REALIZATION
│
├─ Implementation
│
PROOF
│
├─ Verification
├─ Operation
└─ Learning
```

I think this is close to a **universal engineering decomposition**.

---

## One distinction I would strongly preserve

A lot of development processes become unnecessarily complicated because they mix four fundamentally different questions:

| Question                                   | Correct level         |
| ------------------------------------------ | --------------------- |
| **Why should we do this?**                 | Problem / Purpose     |
| **What must be true?**                     | Requirements          |
| **How should the solution be structured?** | Architecture / Design |
| **Did it actually work?**                  | Evidence              |

Keeping these separate gives you a powerful rule:

> **Purpose should not accidentally dictate implementation. Requirements should not accidentally become architecture. Architecture should not unnecessarily dictate code. Tests should prove requirements rather than implementation preferences.**

That creates both **control and implementation freedom**.

### My preferred canonical structure

For something you could use as the backbone of Codeos, EvidenceAtlas, a physical engineering project, or even a business process, I would settle on:

> **1. Problem → 2. Vision → 3. Outcomes → 4. Scope & Constraints → 5. Requirements → 6. Architecture → 7. Design → 8. Detailed Specification → 9. Implementation → 10. Verification → 11. Operation → 12. Learning**

But I would **not create twelve mandatory documents**. These are twelve **questions/levels of reasoning**. A small project might express them in three artifacts; a large safety-critical system might need dozens.

That distinction—**universal reasoning structure, but variable artifact structure**—is important if the goal is high quality without process bloat.

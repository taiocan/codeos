## Step 1 — Change Intent

### Problem

A downstream DBA project's local evidence (behavioral tests passing, replay verification
clean, schema conformance holding) can silently diverge from what CI actually checks, if CI
was never told what DBA-specific evidence exists to check in the first place. Codeos has no
documentation mapping its evidence types onto concrete CI gates — a project adopting CI has
to invent this mapping from scratch.

### What changes

| File | Change |
|---|---|
| `docs/ci-integration-profile.md` | New: maps the 7 evidence types named in the UPG-0019 backlog brief onto illustrative CI job/step definitions a downstream DBA project can optionally adopt |
| `backlog/UPG-0019-ci-profile.md` | Feature Thread: CHG-20260706-001 activated (done) |
| `backlog/features.md` | Row → IN_PROGRESS (done) |
| `status/self-development.md` | Row activated (done) |

### Scope boundary — what stays the same

- **`dba-system.md` — not touched.** This is documentation guidance, not downstream
  doctrine — matching UPG-0016's (Workflow Profiles) precedent exactly: a `docs/` reference
  file a downstream project may optionally read, not something `dba-init.sh` installs or
  `dba-system.md`'s stage table references.
- **No real CI added anywhere** — not to Codeos's own repo, not as a template a downstream
  project's `dba-init.sh` run would install. This is guidance/mapping only, matching the
  backlog's own Guardrail ("Start with minimal checks") and DBA-philosophy note ("No rule
  touched... reinforces, rather than alters"). Explicitly confirmed with the human before
  drafting this Step 1 (two options were offered: docs-only vs. also wiring real CI onto
  Codeos's own `tools/reviewer` crate; docs-only was chosen).
- **No existing subcommand or tool behavior changed** — `check-drift` (UPG-0020) is
  *referenced* by this doc as the concrete mechanism for the "stack manifest reconciliation"
  check, not modified.
- **`docs/workflow-profiles.md` (UPG-0016) — not modified.** Distinct concern (branch/PR
  discipline vs. evidence-to-CI-gate mapping); the new doc may cross-reference it, not merge
  with it.

### Design intent

New file `docs/ci-integration-profile.md`, structured as one section per evidence type from
the backlog's "Proposed artifact(s)" list, each with: what DBA evidence it checks, why it
matters, and an illustrative (language-agnostic where possible) CI step sketch:

1. **Behavioral tests** — run the project's Stage 5 behavioral test suite; fail the build on
   any failure.
2. **Replay tests** — run Stage 5/8 replay verification tests; fail on any failure.
3. **Schema conformance tests** — verify captured runtime events conform to the approved
   event schema (Stage 8 evidence); can be folded into replay tests or run as a distinct step.
4. **Lint/typecheck** — standard language-appropriate static checks (illustrative only — "use
   your project's normal lint/typecheck tooling").
5. **No unapproved event names** — a check that diffs emitted event names (from a runtime log
   sample or replay fixture) against the approved event schema's named events; fails if an
   emitted name isn't in the schema.
6. **No raw runtime log leakage** — a check that `events/runtime_events.jsonl` (or excerpts
   committed as fixtures) don't leak unsanitized secrets/PII; illustrative grep-for-known-
   patterns sketch, not a new tool.
7. **Stack manifest reconciliation if dependency/config changed** — the one check with an
   already-built, concrete mechanism: run `codeos-reviewer check-drift --base <ref>` (UPG-0020)
   as a CI step. Exits 6 if a watched dependency/config file changed without a
   `stack-reconciliation-report.md` in the diff; CI treats a non-zero exit as a failed gate.

Every section states explicitly: **optional, illustrative, not enforced by Codeos** — a
downstream project adapts these sketches to its own CI system (GitHub Actions, GitLab CI,
etc.), language, and risk tolerance. No non-negotiable rule requires any project to adopt
this doc's suggestions.

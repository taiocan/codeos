# Review Policy — v15

v15 incorporates v14 in full except where this version supersedes it. It separates review
failures into three domains so that only development failures consume semantic review capacity.

## Failure domains

A **development failure** is a substantive finding that the implementation, governed meaning,
architecture, evidence validity, safety, or integrity does not satisfy approved behavior. It is
the only result that may produce `DO NOT ADVANCE` and consume semantic review capacity.

`REVIEW_NOT_READY` means the Review Readiness Gate failed. The reviewer is not invoked, no review
round or bounded mechanism is consumed, and no governance state changes. It carries one reason
code. Unavailable infrastructure, toolchain mismatch, packet, identity, and evidence defects are
reason codes, not separate states.

`REVIEW_EXECUTION_INVALID` means the reviewer was invoked with ready inputs but its response fails
structural validation. The raw attempt is preserved immutably. It records no semantic conclusion,
consumes no review round, authorization, or bounded mechanism, and remains eligible for
re-execution with the identical Review Input Manifest without limit. Automatic re-execution within
one review command is bounded; further attempts require a new command.

## Review Readiness Gate

Every reviewer invocation, for every review operation, MUST first pass one deterministic Review
Readiness Gate. The gate establishes that the execution environment and reviewer toolchain are
usable, that every identity in the Review Input Manifest is mechanically derived and coherent,
that the reviewed-state snapshot is reconstructible, and that every required input is
inspectable within the packet. Any failure is `REVIEW_NOT_READY`.

Identities are machine-owned. The reviewer tool derives every identity it can compute from a
locally available canonical artifact. A supplied identity is only an expected value; disagreement
fails the gate. The Review Input Manifest is the single source for packet construction and review
lineage validation.

## Scope-aware coverage

The required input set is derived deterministically from the review operation and its manifest,
never from caller exclusions. It cannot be narrowed by the caller. `FULL_COVERAGE` means every
required input is inspectable. A required input that is absent, summary-only, or not inspectable
fails the gate. Material outside the required input set does not lower coverage. Redaction of a
required input keeps its existing coverage treatment.

## Superseded rules

- Readiness applies to every reviewer invocation, not only Stage 8. Partial coverage of a required
  input is a readiness failure (v3).
- A malformed or structurally incomplete response is `REVIEW_EXECUTION_INVALID`. It does not
  consume a bridge retry, closure, replacement, or correction (v10, v11, v12).

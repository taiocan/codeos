# Codeos Mechanics Policy — v5

## Purpose

v5 retains v4's fixed set and applicability. It strengthens `product_journey`: the test observes a
Codeos-derived transition definition and reports runtime facts against it, rather than asserting
its own topology.

## Fixed Set

### Delivery

| Mechanic | Applies | Requirement |
|---|---|---|
| `vertical_slice` | always | Deliver every touched Platform Baseline tier together in one bounded cycle. |
| `early_gui_preview` | always_when_gui | Show the unverified Early Development Preview after basic integration smoke and before full verification. |

### Validation

| Mechanic | Applies | Requirement |
|---|---|---|
| `smoke` | always | Run integration across every touched tier before deeper verification. |
| `product_journey` | always | Execute the primary production journey through the applicable frontier and emit structured runtime observations against the transition definition Codeos derives from approved authority. |
| `behavior` | always | Verify the approved Contract behavior. |
| `repeatability` | always | Produce replay and idempotency evidence where repeated execution or the Event Spine makes it applicable. |
| `data_integrity` | always_when_persistence | Against real PostgreSQL, verify required state, invalid-state rejection, clean migration, and applicable transaction atomicity. |
| `playwright` | always_when_gui | Demonstrate the critical user-visible outcome through real PostgreSQL, Rust, and Svelte tiers. |
| `human_ux` | always_when_gui | Obtain human validation that the behavior is usable and matches expectation. |

### Communication

| Mechanic | Applies | Requirement |
|---|---|---|
| `summary_first` | always | Open every substantial downstream artifact with the layout-contract Summary block. |
| `reader_oriented_writing` | always | Apply the Reader Output policy selected by the canonically resolved project configuration, or unversioned guidance only when the composition selects none. |
| `terminology_consistency` | always | Reuse canonical terms, verify references, and add an authorized semantics-critical term in the same change. |

## Product-journey evidence protocol

Before execution, Codeos writes the expected journey definition to a temporary file and supplies
`CODEOS_EXPECTED_FRONTIER`, `CODEOS_JOURNEY_DEFINITION_PATH`, and
`CODEOS_JOURNEY_EVIDENCE_PATH`. The runner reads the definition and writes one JSON object containing
only `schema`, `journey_id`, `target_frontier`, `setup`, and ordered runtime `observations`.

Each observation contains `transition_id`, optional `handoff_identity`, `state_origin`, `result`,
and optional `reason`. It MUST NOT restate producer, handoff type, consumer, endpoints, or authority.
A pass requires a concrete handoff identity. A failure is the final observation and states its
reason. The command result and observed prefix must agree.

Setup categories are exactly `infrastructure`, `actor_identity`, `static_reference_data`, and
`external_boundary_simulation`. `state_origin: production` means the intermediate domain handoff
was created through the production capability responsible for it. A protocol-faithful simulated
external boundary may feed the real adapter; direct insertion of its downstream domain object is
not production creation.

An optional project-local `runtime_verification.journey_guard_script` may sandbox the canonical
runner. It strengthens runtime isolation but is not a universal conformance requirement.

## Configuration Display

The project's `mechanics:` block remains a transparency view, not a selection surface, and contains
the exact v5 set and values.

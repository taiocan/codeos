# Codeos Mechanics Policy — v1

## Purpose

Doctrine names the Codeos Mechanics as fixed obligations without enumerating them. This policy
owns the canonical vocabulary: the exact name, semantics, and applicability of each mechanic. A
project's configuration selects nothing here — every mechanic below is always in effect wherever it
applies. Configuration only displays this set for transparency.

## The Fixed Set

Grouped by concern. `always` applies unconditionally to every feature; `always_when_gui` applies
whenever the feature's Contract includes a GUI-visible outcome, and is derived from that fact, not
chosen by a project.

### Delivery

| Mechanic | Applies | Requirement |
|---|---|---|
| `vertical_slice` | always | A feature's implementation proceeds through every Platform Baseline tier it touches together, inside one bounded delivery cycle, rather than tier-by-tier across separate cycles. |
| `early_gui_preview` | always_when_gui | The Early Development Preview doctrine defines: an unverified, clearly labeled preview after basic integration smoke, before the full verification loop proceeds. |

### Validation

| Mechanic | Applies | Requirement |
|---|---|---|
| `smoke` | always | The feature's DB↔backend↔GUI (or whichever tiers it touches) integration actually runs before deeper verification begins. |
| `behavior` | always | Approved Contract behavior is verified, per Stage 5. |
| `repeatability` | always | Replay and idempotency evidence is produced where the event spine or repeated execution makes it applicable, per the existing replay mechanism. |
| `playwright` | always_when_gui | At least one bounded, integrated Playwright journey demonstrates the feature's critical user-visible outcome against the real Postgres, real Rust backend, and real Svelte app — no tier mocked. Consult `dba/05-guidance/patterns/svelte-gui-verification.md` for technique; this mechanic makes its application mandatory rather than advisory-when-selected. |
| `human_ux` | always_when_gui | The human validates that delivered behavior matches expectation and is usable — distinct from, and in addition to, behavioral correctness. |

### Communication

| Mechanic | Applies | Requirement |
|---|---|---|
| `summary_first` | always | Every substantial human-facing artifact opens with a Summary block after frontmatter, per the Downstream Project Layout Contract. |
| `reader_oriented_writing` | always | Every human-readable output applies `dba/05-guidance/reader-oriented-output.md`, including a declared reader-model progression on substantial narrative artifacts. |
| `terminology_consistency` | always | Canonical terms are reused, broken terminology references are caught mechanically, and a new semantics-critical term is added to `terminology.md` in the same change. |

## Configuration Display, Not Selection

A project's `codeos.yaml` may list these mechanics under a `mechanics:` block for visibility. Any
value present there MUST match this table exactly (`always` or `always_when_gui` as shown); a
configuration that attempts to set a different value, remove an entry, or mark one `conditional` or
`not-applicable` is invalid and fails closed. `always_when_gui` mechanics are never independently
disabled — they turn off only as a structural consequence of a feature having no GUI-visible
outcome, or of the project's Charter recording the GUI tier itself as not-applicable under the
Platform Baseline.

## Extension

A mechanic outside this defining set (for example accessibility, security, or performance
verification) is not shipped by v1. When one is later adopted, it is added to the Validation group
above as a genuinely project-selectable entry (`required | conditional`, with a recorded reason for
`conditional`) in a new policy version — never by reinterpreting or loosening a mechanic already
listed as fixed here.

# Reader Output Policy — v3

## Purpose

Human-facing output uses progressive disclosure: give the minimum information needed for the
human to make the current decision correctly. Correctness, semantic separation, status separation,
and navigable detail remain mandatory while inline compactness becomes operational.

## Scope

The four v2 tiers remain in force:

1. All Codeos-owned human-readable content follows D10's semantic structure.
2. Canonical toolkit components under `dba/` orient before detail, while no specific heading is mandatory.
3. Substantial downstream narrative artifacts carry the layout-contract metadata and Summary.
4. Substantial inline agent responses follow the compact progression below without metadata.

A canonical toolkit component carries neither the `reader_model` field nor a required Summary;
it is not a downstream artifact instance.

## Compact Inline Response

Substantial inline responses follow this logical order. These are semantic blocks; headings are
optional, and empty blocks are omitted.

1. **Core** — state the result, recommendation, or required decision first. Include the next action
   when one exists. A simple response may contain only this block.
2. **Reasons** — normally include no more than three reasons that could affect the decision.
3. **Evidence** — normally include no more than three strongest direct evidence items or artifact
   references.
4. **Terminology reference** — optional; use only when several canonical definitions materially
   help review.

Define a semantics-critical specialized term briefly on first use whenever comprehension depends
on it. Do not defer a necessary definition to the terminology reference.

Exceed the Reasons or Evidence defaults only when omission could materially change the human's
decision or make the response misleading. Do not satisfy compactness by mixing decisions,
observations, reasoning, evidence, assumptions, unresolved gaps, and actions.

Do not narrate routine work, restate the request, list unchanged components, report routine PASS
results, or append the complete analysis unless it is needed for the current decision. Expand on
request.

## Artifacts and Reader Models

The v2 requirements for substantial downstream artifacts remain unchanged: use an applicable
reader model, declare it where the layout contract requires, open with the required Summary block,
and preserve navigable supporting detail. Compact inline presentation never removes content that
an artifact's owning contract requires.

Use the simplest reader-model progression that fits the content:

- **Stable Topic** — keep several facts under one recognizable subject.
- **Known-to-New** — connect each reasoning step to established context before introducing the next.
- **Whole Before Parts** — name the whole or relationship before describing its components.
- **Preview Then Traverse** — preview several important findings, then explain them in that order.

A reader MUST be able to move from the result or Summary to the relevant section and supporting
evidence without reading everything sequentially. Decisions, observations, reasoning, evidence,
assumptions, unresolved gaps, and next actions MUST remain distinguishable.

## Review

Review presentation independently from correctness. A response fails this policy when its core
result is not available first, routine detail obscures the decision, necessary terminology arrives
too late, or reasons and evidence exceed the defaults without a decision-safety need.

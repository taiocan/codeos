# Workflow Governance Policy — v1

## Purpose

Doctrine names three governed workflows and requires their checkpoints to be mechanically verified.
This policy owns the mechanism common to all three: how a checkpoint's state is derived, when a
later checkpoint is blocked, the result vocabulary, the decision-receipt format, and the closed set
of decisions that need a receipt. Each workflow contract owns only its own checkpoints and routes.

## Checkpoint State

A checkpoint is in exactly one state:

| State | Meaning |
|---|---|
| `PASS` | Every required condition for this checkpoint is currently established. |
| `BLOCKED` | A required condition is not established, or a required earlier checkpoint is not `PASS`. |
| `WAITING` | The checkpoint's own conditions are met but it is waiting on a human decision that only a person can make (a preview direction call, a route classification, an acceptance). |

State is derived, never stored. It is recomputed on every query from three evidence classes and
nothing else:

1. **Canonical state** — approved artifacts and their approval metadata (`approval`, or the
   Specification Package's `status` / `approved_by` / `approved_at` triple), the project
   configuration and its validity, binding currency, and the reviewer tool's existing assessment
   records and decision log. Cheap deterministic predicates, re-evaluated live.
2. **Verification records** — mechanical verifications the `check` command actually executed and
   that passed, persisted as described below.
3. **Decision receipts** — the closed set of irreducible human / authorized-agent decisions below.

A manually maintained checklist is never authority for a checkpoint. A checkpoint PASS is never
reconstructed indirectly: a later receipt never stands in for an earlier verification, and no
special case exists whose only purpose is inferring that an earlier verification must have passed.

## Fail-Closed Ordering

Checkpoints within a workflow are strictly ordered. A later checkpoint cannot be `PASS` while a
required earlier checkpoint is `BLOCKED` or `WAITING`. Work performed *inside* a checkpoint — how
tests are written, how an implementation is structured — stays flexible; only the ordering between
checkpoints is fixed.

A blocked checkpoint reports the exact unmet condition, the evidence or path involved when known,
why the condition applies to this subject, and one concrete next action. It never reports a bare
"blocked" or "workflow failed".

## Command Responsibilities

- `status` and `next` are read-only. They derive state from the three evidence classes and never
  execute a verification or write anything.
- `check` executes the mechanical verifications a subject still needs — those with no current
  verification record — against the real stack, in checkpoint order. On each pass it writes or
  updates that verification's record. It stops at the first failing verification, and at the first
  checkpoint it cannot advance (one waiting on an approval, a receipt, or review). It never writes
  a decision receipt.
- `decide` records one decision receipt from the closed set below. It never manufactures mechanical
  PASS evidence.

## Mechanical Verification Records

The verification store is the append-only file `.codeos/06-workflow/verifications.jsonl`, one JSON
object per line. A record identifies at least:

- `workflow`, `subject`;
- `checkpoint` and `verification` (the mechanic identity, e.g. `smoke`, `baseline`);
- `result` — always `passed`; a failing verification is not persisted;
- `bindings` — the governed inputs and implementation state it was executed against, each with its
  content hash at execution time;
- `command` — the command line that was run;
- `timestamp`.

A verification record is evidence that the named verification ran and passed against that exact
state. It makes **no** adequacy judgment — it does not assert the behavior is correct, only that
the verification executed and passed. It ceases to establish its checkpoint the moment any bound
input no longer matches its current hash; staleness reporting names the drifted binding and shows
the previous and current hash. Records are invalidated by drift, never deleted.

Governing rule: **a checkpoint `PASS` comes from a currently evaluated live predicate, a current
verification record, or a current decision receipt; it is never inferred from an unpersisted
historical command execution.** Mechanical results are recorded as verification records, never as
receipts — receipts are for irreducible human and process decisions only.

## Decision Receipts

The receipt store is the append-only file `.codeos/06-workflow/decisions.jsonl`, one JSON object
per line:

```json
{
  "workflow": "feature",
  "subject": "F-0012",
  "checkpoint": "early_preview",
  "result": "direction_confirmed",
  "bindings": { "intent": "<sha256>", "contract": "<sha256>", "event_schema": "<sha256>", "implementation_state": "<sha256>" },
  "timestamp": "2026-09-05T12:00:00Z",
  "rationale": "optional; required only for no_action"
}
```

- `bindings` names every governed input the decision depended on, each with that input's content
  hash at decision time. `implementation_state` is a content hash over the relevant working-tree
  files, **not** a commit SHA — a preview is allowed against uncommitted work.
- A receipt no longer establishes its checkpoint the moment any one binding no longer matches its
  input's current hash. Staleness reporting names the specific binding that changed and shows the
  previous and current hash. Receipts are invalidated by drift, never deleted.
- A receipt is evidence of workflow progression only. It is never a governing artifact and never
  overrides the meaning of the Charter, a Specification Package, an Architecture Scope, or any
  human-control boundary (doctrine, Decision Receipts).

### The closed set of receipt-bearing decisions

Exactly these seven, and no others. A new receipt-bearing decision requires a new version of this
policy.

| Receipt | Workflow / checkpoint | Why it cannot be reconstructed |
|---|---|---|
| Initial Product Preview | bootstrap / B4 | The human's first direction call on the running baseline; no artifact records it. |
| Early Development Preview outcome | feature / F4 | The human's direction call mid-implementation; `direction_confirmed`, `behavior_revision_required`, or `implementation_or_ux_refinement_required`. |
| Reconciliation completion | feature / F6 | Stage 7 persists no durable file. `result: completed`, independent of how many `GAP` rows the reconciliation honestly records. |
| Final Human UX Validation | feature / F8 | The human's judgment on the fully verified result, distinct from F4. |
| Acceptance | feature / F9 | No `ACCEPTED` status exists anywhere; Stage 8 persists no durable report. |
| Operation route selection | operation / O2 | The human's semantic classification of an observation; the one decision the tool must never infer. |
| `no_action` closure | operation / O5 | The only O5 branch with no downstream artifact whose completion could otherwise prove closure; requires `rationale`. |

Normal-route O5 closure is **not** a receipt: it is derived from the routed work's own completion
and verification evidence (a refinement accepted, a revised Specification Package approved, a new
feature accepted). Independent review (F7) is **not** a receipt: it is covered by the reviewer
tool's existing assessment records and decision log.

## Compatibility

A DBA-5 project has no `.codeos/06-workflow/` directory, no receipts, and no verification records.
Adopting DBA-6 derives as much workflow state as possible from the project's existing canonical
evidence. It never manufactures a historical preview, validation, or acceptance receipt, or a
historical verification record, for an action that was never recorded; where a forward checkpoint
needs evidence an older project never produced, the requirement applies prospectively at that
checkpoint's next occurrence — `check` produces the missing verification record on its next run.

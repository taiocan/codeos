# Operation & Learning Workflow Contract — v1

## Purpose

Ensure every material post-acceptance observation ends in one valid route and a verified
resolution, without becoming a linear feature-style pipeline. The route vocabulary is doctrine's
existing Post-Acceptance Learning table; this contract mechanizes its use, it does not invent
routing authority. The common mechanism is owned by the Workflow Governance policy.

## Checkpoints

### O1 — Observation

- A concrete observation is stated (a defect, UX friction, a data-quality issue, a performance
  problem, a changed external condition, a new user need).
- A source or evidence reference exists where one applies.

Ordinary log lines do not enter this workflow. An observation has no durable identity of its own:
its identity for the purpose of O2's receipt is a short subject slug plus a content hash of the
observation statement, carried in the receipt.

### O2 — Route decision

A human or authorized agent semantically classifies the observation. Exactly one route is selected
and recorded as the Operation route selection receipt (Workflow Governance, closed set), bound to
the observation statement's content hash and the current governing artifacts the route depends on.

| Route | Meaning | Doctrine row |
|---|---|---|
| `implementation_defect` | Approved behavior is still correct; the implementation does not meet it. A presentation-only correction within approved behavior is this route with lighter verification, not a separate route. | Targeted refinement |
| `new_feature` | A new capability. | New Intent |
| `specification_change` | An approved requirement is wrong or incomplete. | Affected Specification Package |
| `charter_change` | Solution purpose, an outcome, scope, or a System Constraint changed. | Solution Charter |
| `architecture_reassessment` | Approved architecture no longer satisfies approved requirements. | Applicable architecture policy |
| `no_action` | Observed, considered, and deliberately no change; requires a recorded rationale. | Observed and deliberately not acted on |

`defer` is not a route: an observation that is material but not yet routable is held in the
Learning Register and returns to O2 later. Every route above is a row in doctrine's Post-Acceptance
Learning table; this contract adds none.

The tool validates only that a route was chosen, that it is one of the above, that `no_action`
carries a rationale, and that the decision is bound to the observation. It never selects the route.

### O3 — Routed action

The selected route is enforced mechanically:

| Route | Enforced path |
|---|---|
| `implementation_defect` | targeted repair path — full behavioral re-verification, or browser and human validation only for a presentation-only correction within approved behavior |
| `new_feature` | Feature Development from F1 |
| `specification_change` | Specification Package revision → Feature Development |
| `charter_change` | Charter revision and impact assessment → affected work |
| `architecture_reassessment` | architecture reassessment and approval → affected work |
| `no_action` | → O5 closure with rationale |

### O4 — Verification

Where a change was made, proportional evidence exists that the routed action resolved the
observation. A conformance repair that changes no approved meaning does not require the full Feature
Development workflow. A shared change carries impact-scoped regression evidence.

### O5 — Close

An observation may close only when its route was completed, its required verification exists, the
resulting commit or accepted artifact is linked, and terminology was updated where meaning changed.

Normal-route closure is **derived** from that routed work's own completion and verification
evidence — no separate receipt. Only `no_action` closure has its own receipt, because it is the
one branch with no downstream artifact from which closure could otherwise be established. Nothing
closes into an informal note.

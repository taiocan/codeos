# Architecture Synthesis Policy — v3

## Conditional Architecture Boundary

Architecture Synthesis is a conditional project-level approval gate, not a numbered feature stage.
It applies when implementing one or more features would otherwise require an unresolved decision
about project-level structure or a structural boundary shared by features. Relevant decisions
include responsibility or data ownership, dependency direction, persistence, integration, shared
infrastructure, and deployment or runtime topology.

Sharing a runtime, database, or technology does not by itself trigger the gate. A feature also need
not be coupled to another feature for the gate to apply: a single feature that would establish or
change a project-level boundary requires architecture synthesis.

At Specification Package approval and again at Stage 4 entry, ask whether implementation would
otherwise settle such a decision. If not, implementation proceeds without an architecture artifact.
If yes or genuinely uncertain, architecture remains unresolved and implementation must stop.

## One Authoritative Artifact

Each architectural scope has exactly one current artifact:

`.codeos/02-architecture/scopes/<scope-id>.md`

The filename is the scope identity. Front matter contains exactly two governance fields:

```yaml
features: [F-0001, F-0002]
approval: null
```

`features` is the sole authority for scope membership. It must be non-empty and duplicate-free, and
a feature may appear in at most one current scope artifact. Duplicate membership is an unresolved
conflict and blocks implementation. Architecture membership or approval must not be copied into
another operational record. Unknown governance fields are invalid so a second status or ownership
mechanism cannot silently emerge beside these fields.

`approval: null` means draft or otherwise unapproved. Approval records one explicit human decision:

```yaml
approval:
  by: Human name
  at: 2026-08-12
```

Both values must be non-empty. Editing metadata does not itself constitute approval. Any material
change to architecture content or membership first returns `approval` to `null`; Git and human diff
review govern that discipline. There is no content hash or separate integrity protocol.

Git is the version and history mechanism. Architecture artifacts have no independent version field,
manual history copy, current-version pointer, or compatibility state.

## Inputs and Authority

Every feature listed in a scope must have an approved, mutually consistent Specification Package
before that scope can be approved. Synthesis may be drafted earlier, but it cannot use sibling drafts
or assumptions as authority.

Architecture may constrain structure but must not invent or override behavior or quality
requirements. A decision must derive from approved requirements or an explicit human architectural
decision.

Approved quality requirements and System Constraints are inputs to synthesis. Architecture responds
to them by recording the structural consequences they force; it never originates them. Keep the two
distinguishable: "search response within 500 ms under workload X" is a requirement, and "query
execution must avoid scanning the complete corpus" is the architectural consequence.

When synthesis exposes a missing requirement, return it to its owning source rather than resolving
it in architecture:

- behavioral gap → the affected Intent, Contract, or Event Schema;
- feature-specific quality requirement → the affected Contract;
- cross-cutting quality requirement or other System Constraint → the Solution Charter.

## Synthesis Reasoning

Architecture synthesis considers:

1. **Context & Boundary** — what is in scope, outside it, or externally relevant?
2. **Structure & Responsibility** — what major architectural components exist, and what does
   each own?
3. **Interactions & Dependencies** — how do those components communicate and depend on one
   another?
4. **Data & Runtime** — who owns state, where does it persist, and where and how does execution occur?
5. **Constraints & Decisions** — what approved constraints and explicit architectural decisions must
   implementation preserve, and what structural consequences follow?

These are reasoning prompts, not required headings, checklist items, schema fields, or a completeness
taxonomy. Record only answers that establish or constrain project-level architecture. Do not add
empty sections or `N/A` entries. Apply the doctrine's structural-ownership boundary to decide what
belongs here: a decision that is local to one component and reasonably reversible stays with
implementation.

Every architectural component introduced or governed by the scope must have a clear owned
responsibility. Record its interfaces, state, runtime placement, or constraints only when relevant.

Synthesis must identify unresolved overlapping responsibility, incompatible dependency direction,
conflicting data authority, contradictory lifecycle or failure assumptions, and incompatible
integration or event semantics. Checks have no decision authority, but a material unresolved
conflict makes approval unsupported.

## Feature Applicability

Record a feature-specific obligation only when shared architecture materially constrains that
feature. The artifact must make the affected feature identifiable, but no fixed obligations table
or separate per-feature architecture artifact is required. Decisions deliberately left local to
implementation may be stated when doing so prevents accidental overreach.

## Approval and Delivery Eligibility

The synthesis workflow is:

1. Verify scope membership and approved Specification Packages; review them together for structural
   conflicts and unresolved architecture.
2. Resolve and record only the minimum project-level architecture and applicable feature obligations
   needed for safe independent implementation.
3. Present the complete scope artifact for one explicit human approval and record the approving
   person's name and date under `approval`.

At Stage 4, obtain deterministic scope facts from the architecture inspector:

- No matching scope and no unresolved architecture-significant decision: proceed.
- Exactly one matching, well-formed scope with non-null approval: proceed under its constraints.
- A matching draft scope, duplicate membership, malformed metadata, incomplete approval metadata, or
  a newly discovered unresolved architecture-significant decision: stop and return to synthesis.

The inspector reads and validates scope metadata only. It does not judge architectural sufficiency,
approve an artifact, or decide whether the gate applies.

Architecture approval is additional to Specification Package approval, not a replacement for it.

## Change and Reassessment

A material change to approved architecture or membership sets `approval: null` before the
replacement decisions are used. Reassess only affected specifications and completed work. Existing
implementation is not invalidated merely because the artifact changed; reconciliation is required
only where targeted impact assessment identifies an actual conflict.

Reviewer conclusions remain advisory. Review timing and waiver behavior are owned by the selected
review policy; architecture review introduces no additional approval state.

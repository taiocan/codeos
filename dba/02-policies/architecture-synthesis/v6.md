# Architecture Synthesis Policy — v6

## Purpose

v6 retains v5's conditional gate, one-artifact model, authority boundary, approval mechanics,
Platform Baseline resolution, and reassessment rules. It gives shared product-journey topology a
deterministic representation inside the existing Architecture Scope.

## Cross-feature transition definitions

When consecutive journey frontiers are owned by different Specification Packages, exactly one
approved Architecture Scope containing both features defines the transition under
`## Primary Journey Transitions`:

```yaml
transitions:
  - transition_id: T-0001
    from_frontier: retrieval
    to_frontier: corpus
    producer_feature: EA-0016
    producer_role: research-api
    handoff_type: RetrievalRun
    consumer_feature: EA-0003
    consumer_role: corpus-coordinator
```

`transition_id` is project-unique and uses `T-####`. Both features remain members of the scope's
frontmatter `features` list; the transition mapping does not create a second membership authority.
The definition records structural roles and handoff type, not behavioral guarantees or runtime
identities.

A missing, duplicate, conflicting, malformed, or unapproved cross-feature definition leaves the
existing architecture decision unresolved and blocks the affected journey verification. A
transition wholly inside one Specification Package may remain under feature-local implementation
authority and needs no Architecture Scope merely to fill this structure.

## Evidence relationship

Codeos derives expected transition identity, endpoints, producer role, handoff type, consumer role,
and authority from approved artifacts. Journey runners report only observed runtime identity,
production origin, and pass/failure. Architecture never records runtime results, and verification
evidence never becomes topology authority.

All other Architecture Synthesis v5 requirements remain in force, including returning material
changes to `approval: null` before use.

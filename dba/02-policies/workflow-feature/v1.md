# Feature Development Workflow Contract — v1

## Purpose

Carry one capability from specification through acceptance. Repeated once per feature. The common
mechanism — state derivation, fail-closed ordering, result vocabulary, receipts — is owned by the
Workflow Governance policy. Codeos Mechanic names and their applicability are owned by the selected
Codeos Mechanics policy.

Mechanizing these checkpoints does not raise any acceptance bar. A checkpoint verifies that the
evidence a decision needs exists and is current; it never demands a stronger result than the rest
of DBA already requires.

## Checkpoints

### F1 — Specification

- Intent, Contract, and Event Schema exist at their canonical paths.
- All three record the joint Specification Package approval (`status: APPROVED` with non-empty
  `approved_by` and `approved_at`), mutually consistent.
- The Contract's Validation Questions (Behavior, Repeatability, Browser, Preview) are answered.

### F2 — Preparation

- The terminology-consistency check has run against the current artifacts.
- A Design artifact exists where project governance requires one for this feature; otherwise not
  applicable.
- Feature Impact Accounting is complete: for each Platform Baseline tier, `changed` or `unchanged`
  with a reason. A tier is not required to change when the feature does not need it, and a change
  is not manufactured to fill the table.
- The verification approach for each applicable Codeos Mechanic is identified.

### F3 — Vertical implementation

- Every tier the Feature Impact Accounting marks `changed` is implemented and integrated within
  this delivery cycle.
- Basic integration smoke passes (`smoke` mechanic).
- The preview surface is reachable.

For a feature that persists or changes data, the implementation also carries, where applicable: a
versioned SQLx migration; PostgreSQL constraints for durable invariants the database can express
cleanly; parameterized SQL for externally supplied values; an explicit transaction boundary for
atomic multi-step writes. These are implementation requirements, not separate checkpoints.

### F4 — Early Development Preview

Required when the Contract has a GUI-visible outcome. The unverified preview is presented —
*"Development Preview — direction and UX review only; verification is incomplete."* — and the
human's outcome is recorded as the Early Development Preview receipt (Workflow Governance, closed
set), bound to Intent, Contract, Event Schema, and `implementation_state`.

| `result` | Route |
|---|---|
| `direction_confirmed` | → F5 |
| `behavior_revision_required` | → Specification Package revision → human re-approval → F3 |
| `implementation_or_ux_refinement_required` | → F3 → repeat F4 |

F5 is `BLOCKED` until an F4 receipt with `direction_confirmed` exists and is current, wherever F4
applies.

### F5 — Full Verification

Required evidence is derived from applicability. Each applicable mechanic has a mechanical
verification record that `check` persisted on a pass, bound to the Specification Package and the
current implementation state and stale the moment either drifts — never an unpersisted historical
exit code.

Always:

- approved Contract behavior is verified (`behavior` mechanic);
- applicable repeatability evidence exists (`repeatability` mechanic).

When the feature persists or changes data (`validation_data_integrity` mechanic):

- tests run against real PostgreSQL;
- valid required state can be stored;
- relevant invalid state is rejected;
- migration from a clean database succeeds;
- transaction atomicity is demonstrated where applicable.

When the Contract has a GUI-visible outcome:

- component or browser verification where applicable;
- at least one integrated Playwright journey using real PostgreSQL, real Rust backend, and real
  Svelte application, demonstrating the critical user-visible outcome end to end (`playwright`
  mechanic).

Conditional mechanics remain conditional and apply only when the feature introduces the relevant
risk: performance, security, accessibility, concurrency, migration compatibility, data migration,
and future approved mechanics.

Regression evidence is impact-scoped: the feature's own new tests, the affected existing tests
identified from what changed (schema → persistence and data-integrity tests; shared backend
behavior → behavioral and repeatability tests; shared GUI or navigation → Playwright journeys),
plus a small always-run critical-path suite (application starts, user reaches the main workflow, a
critical DB → backend → GUI journey works). Every expensive historical test is not rerun for every
feature.

### F6 — Reconciliation

- A reconciliation has been carried out against the current evidence and its completion is recorded
  as the Reconciliation completion receipt (`result: completed`).
- Every evidence reference the reconciliation cites exists.
- Rows the reconciliation records as `GAP`, `MISMATCH`, or `MISSING` remain represented as such.

`result: completed` does **not** mean zero gaps. A reconciliation that truthfully records
unresolved gaps is complete. Whether an unresolved gap permits progression is decided at F9 under
existing acceptance authority — F6 does not block on it, and the receipt does not demand it.

### F7 — Independent Review

- The reviewer assessment required by the selected review policy exists.
- It is bound to the current reviewed evidence (its recorded packet hash and review commit match
  what would be reviewed now).
- Its outcome permits progression under the review policy.

F7 uses the reviewer tool's existing records; it has no receipt of its own.

### F8 — Final Human UX Validation

Required for a human-facing feature. The human's judgment on the fully verified implementation is
recorded as the Final Human UX Validation receipt (Workflow Governance, closed set), bound to the
Specification Package and the verification state. Distinct from F4: F4 asks whether the direction is
right; F8 asks whether the verified delivered result is acceptable.

### F9 — Acceptance

- Every applicable F1–F8 condition is satisfied.
- The human acceptance decision is recorded as the Acceptance receipt (Workflow Governance, closed
  set), bound to the Specification Package, the verification state, the F6 receipt, the reviewer
  record, and the F8 receipt.

Acceptance authority is unchanged: the human accepts, or requests targeted refinement. After
acceptance the resulting integrated state is the next accepted product baseline, identified by Git
and the accepted artifacts — no new artifact.

# Feature Development Workflow Contract — v8

v8 incorporates v7 and supersedes new writes through the v5 revalidation packet/record lineage.

For new post-acceptance work, the checker derives stale mechanics from current bindings without
reopening unrelated F1–F9 gates. `prepare-candidate --revalidation --trigger <commit>` creates the
one immutable revalidation candidate after eligibility and evidence preflight. A `PASSED`
assessment restores current validity; every other outcome fails closed. No F4, F6, F8, or F9
receipt is created merely to revalidate unchanged meaning.

Changed Intent, Contract, or Event Schema returns to F1 and requires semantic revision. Changed
applicable architecture returns to the conditional architecture boundary and affected preparation,
implementation, verification, and reconciliation; it uses an ordinary candidate and a new F9 but
does not manufacture semantic revision or implementation change. Product UX decisions are reused
when their feature-scoped product binding remains current.

Dependent journey progression excludes stale accepted features and becomes available
automatically when their current validity is restored.

# Feature Development Workflow Contract — v16

v16 incorporates v15 and operationalizes Doctrine v11 Charter obligations. It adds no artifact, review
stage or workflow layer. Every v15 dependency set and record validity rule is unchanged.

## Obligations in the Charter

An obligation is a Charter table row whose first cell matches `O-n`, `R-n`, `C-n` or `M-n`,
optionally followed by a clause suffix `.k` (`R-8.3`), where `n` and `k` are positive integers
without leading zeros. Duplicate IDs fail closed.

When clause rows `X-n.k` exist, `X-n` is a parent. A parent is not itself allocated or verified; its
state is the weakest state of its clauses. Clauses carry the binding text.

**Obligation meaning** is the sha256 of the row's cells after the ID, each trimmed with internal
whitespace collapsed to one space, joined by `\n`. It is independent of the rest of the Charter.

A Milestone row has an `Aggregates` cell naming the obligations whose verification its acceptance
condition requires. A Milestone is verified only when every aggregated obligation is verified.

## Allocation

A Contract scenario heading carries a stable scenario ID `[S-k]`, unique within its Contract and
never reused. The heading may be followed by one or both of these lines:

```text
covers: R-8.1, C-20.2
contributes: R-8.3
```

| Owner | Mandatory checks |
|---|---|
| the one feature whose Contract `covers:` the obligation | every scenario in that Contract that `covers:` it |
| project qualification, for a `C-n` without clauses that no Contract covers | the qualification result for `C-n` |
| the project, for an `M-n` | its aggregated obligations |

When correctness depends on several features, the owner's mandatory checks include a scenario
exercising the integrated product journey through the existing `product_journey` verification.
`contributes:` names a participating feature. It is reported and never establishes any state.
Two features covering one obligation, a reference to an unknown, retired or parent ID, a Milestone
aggregating an unknown ID or itself, and an unallocated obligation are reported findings.

## Evidence

A test is tagged for scenario `S-k` of feature `F-nnnn` when its case ID, lowercased and split on
every character outside `[a-z0-9]`, contains the token `fnnnnsk` (for example `f0004s3`). A case
carrying two tags is valid for both.

Under v16 every `behavior`, `repeatability`, `playwright`, `product_journey` and
`project_qualification` record also records, in `details.obligation_meaning`, the meaning of each
obligation its subject owns or the qualification reports. This is a recorded value, not a
dependency; record validity is unchanged.

A scenario check passes when, for the owning feature, every required verification among `behavior`,
`repeatability` and `playwright` has a current record under the unchanged v15 rules, and their
bound test evidence holds at least one `passed` case tagged for the scenario and no tagged case
that is `failed` or `flaky`. A `skipped` case establishes nothing. A qualification check passes when
the latest candidate `project_qualification` record of any feature is current and reports `pass`
for the constraint. A qualification-owned constraint is SPECIFIED once the Charter is approved.

**Clause-level currency.** A check counts for an obligation only when its record's
`obligation_meaning` for that obligation equals the obligation's current meaning. For this
judgment only, the whole-Charter `charter` binding is replaced by the obligation meaning, so an
edit to another part of the Charter does not stale it. The `charter` binding stays recorded and
keeps governing record validity, F6, F9 and every other existing rule.

## States

| State | Meaning |
|---|---|
| UNASSESSED | no accountable owner, or a reported allocation finding; a legacy Charter's `O-n`, `R-n` and `M-n` start here |
| ALLOCATED | one owner and at least one mandatory check for the current meaning |
| SPECIFIED | ALLOCATED, and the Contract holding the mandatory checks is human-approved; the reviewer's sufficiency judgment informs that approval and never sets the state |
| VERIFIED | every mandatory check passes with clause-level currency |

Evidence without `obligation_meaning`, recorded before v16, never counts as a passing check; the
report names it as legacy evidence. `codeos-workflow obligations` derives the states from the Charter, Contracts and records. Nothing
else stores them. A parent shows the weakest clause state.

## Acceptance and review

F9 for a feature is BLOCKED while an obligation it owns is not VERIFIED. Milestone acceptance is
the existing human decision, and it requires the Milestone VERIFIED.

The existing Specification Package review projects, for each obligation the package covers or
contributes to, the exact clause text beside its scenarios and asks whether a realistic violating
implementation could pass them. The existing Stage 5 review asks whether each scenario's tagged
tests exercise the specified behavior. Both judgments stay advisory.

## Compatibility

Feature Workflow v15 and earlier behave as issued. An approved Charter without obligation clauses
stays valid. Its `O-n`, `C-n` and any `R-n` or `M-n` rows are obligations. Each `C-n` is owned
by project qualification at once; the others report UNASSESSED until a Contract covers them.

Everything else in v15 is unchanged.

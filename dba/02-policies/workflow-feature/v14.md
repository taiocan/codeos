# Feature Development Workflow Contract — v14

v14 incorporates v13 and makes validity dependency-accurate (VALIDITY WO-02, rules R1–R4). A change
invalidates only the decisions whose own dependency set changed. Acceptance, Current Validity,
evidence validity and review are separate decisions.

## Dependency sets

| Checkpoint | Depends on | Recorded, not a dependency |
|---|---|---|
| F4 early preview | Intent meaning; the meaning digests of the feature's F4 claims (`judged_claims`); its Observed Surface; the attesting session outcome | Contract and Event Schema files, product state |
| F6 reconciliation | Intent, Contract and Event Schema meaning; `delivered_state`; `codeos.yaml`; the selected production evidence | — |
| F8 final UX validation | Intent meaning; the meaning digests of the feature's F8 claims; its Observed Surface; the attesting session outcome | the Candidate Bundle, `codeos.yaml`, Contract and Event Schema files |
| F9 acceptance | Intent, Contract and Event Schema meaning; the feature's architecture identity | the Candidate Bundle, `implementation_state`, `codeos.yaml` |

A recorded value that is not a dependency is kept for history and for the rules that read it (the
accepted journey topology and Current Validity read F9's Candidate Bundle). It never makes its
receipt stale.

**F6 after acceptance.** An accepted feature's F6 receipt that differs from the current state only
in its product binding (`delivered_state`) is satisfied by a PASSED Post-Acceptance Dependency
Revalidation of the feature's latest acceptance. No new F6 receipt is recorded. Every other F6
dependency still applies.

**Current Validity** is unchanged. It combines the F9 receipt with the current implementation,
runtime and evidence state of its Candidate Bundle, and a PASSED revalidation restores it without
another F9. It never satisfies F4, F7, F8 or F9; each of those stays current only through its own
dependency set.

## Specification meaning

The meaning identity of an Intent, Contract or Event Schema is the sha256 of the canonical parsed
form of its frontmatter (keys sorted, values as parsed) followed by the exact bytes of its body. A
change to the body's prose is a change, unless a Semantic Equivalence Receipt (Workflow Governance
v6) covers that exact delta for that artifact of that feature. A receipt maps the new identity to
the old one, and identities resolve through receipts, so the decisions that bound the old identity
stay current. Nothing else carries a prose change forward.

Every v14 consumer of the specification compares these identities: receipts, verification records
(so a non-semantic edit re-runs no verification and spends no provider call), a Candidate Bundle's
governed inputs, and Current Validity.

## Evidence identity in Candidate Bundles

A v14 Candidate Bundle (schema 3) cites each verification by its content identity: the sha256 of
the verification's checkpoint, name, result and bindings without `execution_identity`, and of the
evidence content. For a Validation Evidence Set, the evidence content is its environment, execution
inputs, result and observations. For any other record, it is the record's details. Timestamps,
record lines, commands and run IDs are not part of it. `execution_identity` stays the reuse key.

The bundle's configuration identity is the selected reviewer tool contract and review policy (Review
Policy v18), not the bytes of `codeos.yaml`.

No evidence class has a freshness rule in v14; content identity alone governs.

## Compatibility

Feature Workflow v13 and earlier behave as issued. A receipt recorded before v14 is evaluated as
recorded; it carries no v14 dependency keys. A schema 2 Candidate Bundle compares record identities
as issued.

Everything else in v13 is unchanged.

# Feature Development Workflow Contract — v13

v13 incorporates v12, isolates verification by execution environment, and lets one validation run
or human observation serve several features' claims without merging their ownership. Shared
evidence may reduce execution or viewing; it never manufactures claim coverage, human judgment,
review, acceptance, or currency.

## Execution environments

A feature `check` serves one execution environment, stated as `--environment deterministic` or
`--environment production`; deterministic is the default. Codeos never sets, reads, or changes the
project's provider mode. The project serves the stated environment and may refuse a mismatch:
every process a verification starts receives `CODEOS_EXECUTION_ENVIRONMENT` set to it, and every
record such a `check` writes states it as `execution_environment`.

F5 production-source evidence executes only in the production environment. Every other
verification `check` runs executes only in the deterministic environment. A verification the stated
environment does not authorize is never started.

A deterministic `check` runs the stale deterministic verifications of the first unresolved
checkpoint. When that checkpoint then waits only on production-source evidence, it also runs the
stale verifications of each following checkpoint that requires only verifications, up to the first
that requires anything else, and reports the next command: the pre-candidate project qualification
while it is not current, otherwise the production `check`.

A production `check` starts production-source evidence only when F5 is the first unresolved
checkpoint, every verification the deterministic `check` runs before reporting the production
command is current, and the pre-candidate project qualification is current. Otherwise it starts
nothing and reports the next command.

`check --revalidation` applies the same environments to its reruns. A production run starts only
when no deterministic rerun is pending and the pre-candidate project qualification is current.

## Provider-call accounting

Before a production-source run, Codeos creates an empty ledger for it under
`.codeos/06-workflow/provider-ledger/` and passes the run identity in `CODEOS_PROVIDER_RUN_ID` and
the ledger's absolute path in `CODEOS_PROVIDER_LEDGER`. The project's provider adapter appends, for
each provider request, one line before sending it and one line when it ends:

```json
{ "schema": 1, "attempt": 1, "event": "attempt", "at": "<RFC 3339>" }
{ "schema": 1, "attempt": 1, "event": "success", "at": "<RFC 3339>" }
```

`event` is `attempt`, `success`, or `failure`; a timeout is a `failure`. After the run ends, Codeos
counts the ledger: attempted, successful, failed, unresolved (an attempt without an ending line),
and total, which equals attempted. It records the totals beside the ledger and in the evidence
record. The evidence fails when the ledger cannot be counted or when the successful calls do not
equal its distinct provider receipts. A run whose totals were never recorded is counted and
reported by the next production `check`. Codeos sets no provider budget or threshold.

## Validation Evidence Sets

The shared verifications are smoke, the product journey, behavior, repeatability, data integrity,
Playwright, and project qualification. Each run of one, and each shared production run, produces
an immutable Validation Evidence Set under `.codeos/06-workflow/evidence-sets/`, filed by its
execution identity and named by the sha256 of its content. It records the verification, its execution
identity and execution inputs, the outcome, the observations the verification reports (its
Observed Surface; its production observations with their claim IDs), and provenance (command,
times, provider-call totals).

The execution identity is the digest of the verification, the execution environment, and the
execution inputs:

- the implementation state, extended with the content of the build context of every service the
  project's Compose file builds, so a fixture provider or emulator is an execution input;
- `codeos.yaml` and the selected Codeos Mechanics policy;
- for the product journey, the journey definition `check` passes to it;
- for a shared production run, the verifier definition, which names every claim it covers.

When the record of a shared verification is not current, `check` first looks for a passed Evidence
Set with the current execution identity. If one exists, `check` writes the record citing it and executes
nothing; otherwise it runs the verification and stores a new set. A record a v13 `check` writes
binds the execution identity, so a change to any execution input stales it. Runtime-event evidence
(`verify-events`) is not shared.

## Validation claims and attribution

A new or legitimately revised Contract declares its validation claims:

```markdown
## Validation Claims

| Claim ID | Claim | Checkpoint | Evidence |
|---|---|---|---|
| F-0007/route-shown | The road route is shown for the chosen trip. | F5 | run:behavior |
```

- The ID is owner-qualified with the Contract's own feature. The meaning digest is the sha256 of the
  claim text, with whitespace collapsed, and the checkpoint.
- Evidence is `run:<verification>`, satisfied by a passed record of that verification at the
  claim's checkpoint; `observation:production`, satisfied by an observation naming the claim in the
  selected production-source evidence (the claim is also a reality-dependent claim); or
  `observation:human`, satisfied by an explicit Human Validation Session outcome for the claim. Any
  other value, an ID owned by another feature, a duplicated ID, or a claim without its evidence
  fails closed.
- Each Candidate Bundle records the meaning digest of every claim. A claim ID whose digest differs
  from the digest the feature's latest bundle recorded for it fails closed: a changed meaning needs
  a successor ID.
- A Contract without the section keeps its legacy coarse claims `F-NNNN/<checkpoint>/<verification>`.
  Nothing is retrofitted and no history is rewritten.

Validation code may declare coverage but never define a claim. Assertion-level attribution is not
available in v13; a claim needing it cannot be declared.

## Shared production run

`check --environment production` may name several features. Each must satisfy the production
conditions above. The verifier receives one definition (schema 3) naming each feature with its claims and governed
inputs, and returns evidence whose observations carry owner-qualified claim IDs. Codeos stores one
Evidence Set for the run and, for each feature, its own production-source evidence: its claims,
governed inputs, and Evidence Scopes, and the observations of its claims. Each feature's record
cites both and binds only its own claims. A feature not named in the run cannot use the set. A
production `check` naming one feature keeps the v12 verifier protocol.

## Human Validation Session

`codeos-workflow session` without outcomes lists the governed human questions currently waiting
(F4 or F8 for each named feature, with its Observed Surface, whose identity covers every viewport
the journey observed). With outcomes it
records one sealed session at `.codeos/06-workflow/sessions/<sha256>.json`: the implementation and
product state, the environment, every named feature's Observed Surface, and exactly the outcomes
the human stated, one per feature and checkpoint (and claim, for an `observation:human` claim).

- Each outcome is appended as that feature's receipt, binding the session identity, in the same
  operation that writes the session.
- A feature whose current Observed Surface differs from the one the session records, an outcome
  for a feature or question not named, a duplicated outcome, or any addition after sealing fails
  closed. Mixed results are allowed.
- Codeos enforces explicitness only; who may record a decision is governed as for `decide`.

## Accepted journey topology

The accepted journey topology is derived from each feature's latest acceptance and its Candidate
Bundle, whether or not that acceptance is currently valid. Current Validity still decides
consumption: a transition whose producer is not currently valid cannot satisfy a dependent journey,
and an inherited claim from it stays blocked until it is current.

## Compatibility

Feature Workflow v12 and earlier behave as issued. Records, receipts, and bundles written before
v13 are read under the rule they were written under and stay current while it holds.

Everything else in v12 is unchanged.

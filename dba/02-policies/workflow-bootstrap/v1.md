# Solution Bootstrap Workflow Contract — v1

## Purpose

Carry a solution from an approved Charter to a runnable, integrated, minimally verified product
baseline that a human has previewed. Usually performed once. The common mechanism — state
derivation, fail-closed ordering, result vocabulary, receipts — is owned by the Workflow Governance
policy.

Bootstrap does not design the future product. It does not build feature-specific schemas, complete
navigation, a component library, speculative infrastructure, or the final GUI. It answers one
question: can Codeos now deliver the first real feature through the complete solution.

## Checkpoints

### B1 — Purpose

- The Solution Charter exists at its canonical path.
- Any semantics-critical project terminology seed exists.
- The Charter carries a recorded approval (`approval.by` and `approval.at` non-empty).

Semantic authority is the existing `purpose-approval` decision; B1 verifies its evidence is present.

### B2 — Architecture and configuration

- Where consequential architecture requires approval, an Architecture Scope exists with a recorded
  approval and current membership; otherwise this condition is not applicable.
- `.codeos/00-project/codeos.yaml` exists and validates.
- The Platform Baseline is resolved: every tier reads a recognized value, or `not-applicable`
  bound to a reason the approved Charter records.

### B3 — Integrated baseline

`check` executes these against the real stack; on the first full pass it persists one mechanical
verification record (`baseline`). `status` and `next` read that record and never execute the stack.

- PostgreSQL starts.
- A clean SQLx migration succeeds from an empty database.
- The Rust/Axum backend starts.
- The SvelteKit app starts.
- The Docker Compose integration is reachable end to end (DB ↔ backend ↔ GUI).
- The skeleton's shipped unit and component checks pass.
- The skeleton's shipped integrated Playwright journey — real PostgreSQL, real backend, real
  Svelte app — passes.

The B3 record is bound to `codeos.yaml` — the resolved Platform Baseline — and to nothing else. A
Platform Baseline change makes it stale and forces a re-baseline. It is deliberately **not** bound
to working-tree implementation state: Bootstrap is a completed phase, and from the first feature
onward the live integration guarantee is carried by each feature's own verification (F3, F5, F5d,
F5g), not by re-running the skeleton in isolation.

No feature behavior is invented to satisfy B3. A tier the Charter records as not-applicable drops
its corresponding conditions.

### B4 — Initial Product Preview

The running minimal product is presented to the human. This is not feature acceptance. The human's
direction call is recorded as the Initial Product Preview receipt (Workflow Governance, closed
set), bound to the Charter and `codeos.yaml` — the governed inputs the direction call depends on.
It is not bound to working-tree state: each feature increment carries its own Early Development
Preview, and implementing a feature does not invalidate the one-time baseline-direction call.

- `result: direction_confirmed` — progression permitted.
- If the human identifies a solution-purpose or architecture problem, it routes through the
  existing Charter or Architecture Synthesis revision mechanisms; Bootstrap does not resolve it.

### B5 — Ready for first feature

Derived, not decided: B5 is `PASS` when B1–B4 are each `PASS`. No separate human approval and no
"bootstrap complete" field.

## The Bootstrap Gate

While B1–B4 are not all `PASS`, a solution's first Feature Development workflow cannot enter its
first checkpoint. This is the `bootstrap-entry` adapter.

## Re-entry

A later architecture or Platform Baseline change does not rerun Bootstrap. It reassesses only the
B1–B4 conditions that the change can invalidate — a changed persistence boundary is a `codeos.yaml`
change, which makes the B3 verification record stale and calls for a re-baseline, but does not
touch B1. A receipt or verification record whose bindings drift is invalidated by the common
mechanism.

# Implementation Profile Policy — v2

## Purpose and Scope

DBA artifacts through Stage 3 are language-neutral, and this stays true. A project may declare an
**Implementation Profile** — a project-level statement of a preferred implementation language
and its scope — that Stage 4 must consult once approved.

This is an independent, optional mechanism. It does not use architecture-scope membership.

## Profile Lifecycle

**Lifecycle.** A profile has exactly one non-binding pre-approval state: `proposed → approved →
superseded`. A profile becomes `approved` only following an explicit human approval decision;
setting `status: approved` plus `approved_by`/`approved_at` **records** that decision, it does
not **constitute** it — an agent must never move a profile to `approved` merely because the
fields are writable.

## Replacing an Approved Profile

**Immutability and the transition path.** Once `approved`, a profile version is never edited in
place. The current path, `.codeos/02-architecture/implementation-profile.yaml`, always holds only the
current approved version (or a first-ever profile with no predecessor, which may sit `proposed`
directly at the current path — there being no existing binding version it could be confused
with).

A material change (language, applicability, exceptions) is drafted at
`.codeos/02-architecture/proposals/implementation-profile-v<N>.yaml` (`status: proposed`, `supersedes`
pointing at the version it would replace) while the current approved version remains binding,
unaffected, at the current path.

On explicit human approval, in this order: (1) the old current
file moves to `.codeos/02-architecture/history/implementation-profile-v<old-N>.yaml` and its
`status` becomes `superseded`; (2) the proposal is promoted to
`.codeos/02-architecture/implementation-profile.yaml`
with `status: approved`. This ordering means the binding version is never ambiguous — the old
version stays authoritative until the instant its replacement actually takes its place. This is
**only the current approved version is binding for new implementation entry; proposed and historical
versions are never binding.**

## Binding Profile at Delivery Entry

**Binding profile, advisory pattern — kept sharply separate.** Stage 4 must verify that the
implementation is covered by an *approved* Implementation Profile or a recorded exception, within
the profile's resolved scope.

The corresponding technology pattern's recommendations (e.g.
`.codeos/toolkit/dba/05-guidance/patterns/rust-project-structure.md` when `primary_language: rust`) remain advisory —
consulted, never overriding applicable approved project architecture or another project-specific
decision.

This policy introduces no feature-stage decision boundary. If a new profile decision is required,
it must be resolved before the `delivery-entry` doctrine adapter completes. No new Stage ID is
needed.

## Resolvable Applicability

**Resolvable scope — not free text.** `applies_to.scope` is one of `all | feature_ids`. The latter
names exact features. Free-text labels (for example `core-domain`) cannot be mechanically checked
against a specific feature at Stage 4 and are invalid. A profile whose scope is `all` must leave
`feature_ids` empty; a profile whose scope is `feature_ids` must provide a non-empty duplicate-free
list.

## Exceptions

**Exceptions and determinism.** An exception names one `feature_id`, a language, and a required
non-empty rationale. Exceptions are considered only for a feature already within `applies_to`'s
resolved scope. Multiple matching exceptions that disagree make the profile invalid for that
feature; Stage 4 does not pick one arbitrarily.

## Profile–Architecture Conflicts

**Profile–Architecture consistency.** When an approved profile applies and applicable approved
project architecture specifies a different language for that feature than the profile resolves to
(with no matching recorded
exception), this is an **unreconciled contradiction**. Stage 4 must treat it as **ineligible**,
not silently prefer either artifact — the human must add a profile exception or approve a
reconciling profile version before the feature can proceed.

## Implementation Provenance

**Provenance.** When an approved profile applies to a feature, Stage 4's output records the
`profile_id`, `profile_version`, the resolved language, and any matched exception, paralleling
the architecture artifact's role as a binding input.

## Codeos Default and Scaffolding

An absent Implementation Profile imposes no language-profile constraint. When a project chooses to
govern implementation language, it creates
`.codeos/02-architecture/implementation-profile.yaml` from the current optional template and obtains explicit
human approval before Stage 4 relies on it. Initializers do not create an unused proposal.

## Reviewer Coverage

**Reviewer coverage.** This mechanism introduces no new Stage ID. Consultation changes to Stage 4
are covered by the existing Stage ID `4`; onboarding changes are covered by the existing
`onboarding` Stage ID (see "What You Do at Each Stage" below) — no Review Waiver note is needed
the way the Architecture Synthesis Gate needed one.

# Reviewer Tool Contract — v4

## Supported Interface

Use `.codeos/toolkit/dba/04-tools/reviewer/codeos-review.sh` downstream and
`dba/04-tools/reviewer/codeos-review.sh` for Codeos self-development. The wrapper resolves the
compiled reviewer binary relative to the toolkit and delegates these supported operations:

| Operation | External purpose |
|---|---|
| `review` | Build review evidence, invoke Codex, and record the result |
| `plan` | Preview the same validated evidence selection without invoking Codex or writing records, and optionally export the packet |
| `decision` | Append the human decision associated with an automated review |
| `diagnose` | Report resolved reviewer configuration |
| `inspect-architecture-scopes` | Validate and report Architecture Scope metadata without invoking a reviewer |

Use `codeos-review.sh <operation> --help` for exact arguments and options. At a review point governed
by the selected review policy, the usual invocation is:

```text
.codeos/toolkit/dba/04-tools/reviewer/codeos-review.sh review <feature_id> <workflow-or-stage> [artifacts and options]
```

Use Stage ID `3` for the complete Specification Package. The Stage-3 packet evaluates Intent,
Contract, Event Schema, and their consistency.

Support-workflow reviews use `framing`, `decomposition`, or `intake`. The two support-workflow
decision boundaries use `charter` for Solution Charter approval and `architecture` for the
Architecture Synthesis boundary; `architecture` covers both creating a scope and revising an
approved one, because a material change repeats the same boundary. Numeric Stage IDs remain
`1` through `9`. Historical records keep the identifiers recorded when they were created.

Omitting `--base` selects full-file evidence. `--base <ref>` resolves the ref to a commit and selects
changes since that commit. `plan` and `review` apply the same validation, evidence selection, and
packet construction for equivalent inputs; `plan` stops before invocation and durable writes.
Artifact and hash-only paths must resolve to regular files inside the project repository. A symlink
whose target remains inside the repository is valid; a resolved target outside it is rejected.

`plan --emit-packet <file>` writes the packet `review` would send for the same inputs. There is one
packet construction path; the exported bytes are the reviewed bytes. Exporting into the reviewed
working tree is permitted but warned about, because the exported file then becomes evidence in the
next packet.

`review --fresh` starts a new Codex session. Without it, the reviewer may resume saved session state.
`review --scratch` keeps review records in ignored operational state. Session storage, Codex command
flags, JSONL event shapes, process handling, and internal module/type structure are implementation
details rather than compatibility guarantees.

## External Assessment

`review --assessment <file> --packet <file>` records an external assessment: findings produced by a
model Codeos did not invoke, supplied by a human. `--packet` is required and takes the packet
exported by `plan --emit-packet`, together with the `.meta.json` sidecar written beside it. Those
bytes are recorded as the reviewed packet; no packet is rebuilt, so the packet the model read and
the packet the record cites are the same bytes. A sidecar describing a different feature, stage, or
artifact set is refused before any durable write. `--reviewer-label <label>` names that model as descriptive metadata
only; Codeos neither invoked nor verified it and cannot confirm the text originated there.

This path invokes no reviewer and builds no packet. It applies the same response parsing and
fail-closed schema validation as `review`. An unreadable or empty assessment file, a missing or
malformed sidecar, or a mismatched packet fails before any durable write.

An external assessment is not a review. Its record states `source: external`, is sequenced as
`EXT__<feature>__<stage>__A<N>` rather than `REV__…__R<N>`, and does not advance the review round —
the next Codex-backed review of the same feature and stage still claims the round it would have
claimed. Process measurements that describe a run Codeos performed (reasoning effort, reconnects,
wall time) are absent rather than defaulted. Whether an external assessment can satisfy a governed
review obligation is owned by the selected review policy, not by this tool.

Model transport lives outside this tool. `codeos-review-deepseek.sh` is one adapter: packet in, raw
assessment out. It holds no reviewer authority and writes no reviewer record.

## Configuration

Codex is the only reviewer this tool invokes. Optional reasoning effort resolves in this order:
`CODEOS_REASONING_EFFORT`, `.codeos/05-review/reviewer.toml`, then the compiled `high` default.
The configuration file accepts only `reasoning_effort`; malformed configuration and unknown keys,
including retired provider keys, fail before Codex invocation. There is no provider selection: an
assessment from any other model enters through `review --assessment` rather than through
configuration.

## Automated Review Records

The reviewer tool is the single authoritative owner of automated review records. A completed
Codex-backed `review` preserves the reviewed packet and assessment and appends the review result
to the global review log selected for the current project context. `decision` appends its associated
human decision; existing entries and assessments are not rewritten.

The append-only property, the connection between a decision and its reviewed evidence, and visible
handling of incomplete evidence are external integrity guarantees. Exact record structures, storage
subpaths, parsing, sequencing, and algorithms belong to the Rust implementation and tests unless
this contract explicitly makes them compatibility guarantees. The canonical downstream record root
`.codeos/05-review/reviews/` is owned by the Downstream Project Layout Contract.

An empty review packet fails before Codex invocation. A packet reports full coverage only when every
relevant changed file is included, untracked files among them; a file that cannot be shown is
recorded as an exclusion and downgrades coverage. Malformed final assessment output is recorded as
unclassified rather than silently accepted.

Every finding a reviewer declares is either recorded or counted as unrecorded. A reply that declares
findings the record could not capture, or that carries no usable verdict, is recorded with
`parse_status: FAILED` and `assessment_status: INCOMPLETE`, and its effective concern is DO NOT
ADVANCE regardless of the verdict it reported. These apply to every reviewer, not only to external
assessments. `decision` refuses an approval token when required
review provenance is unreadable or evidence coverage is critical or empty unless the human supplies
an explicit override rationale. Reviewer concern levels alone never approve, refuse, or complete a
DBA boundary.

## Authority Boundary

The reviewer is read-only and advisory. Its records provide evidence; they do not own feature
lifecycle state or approval. A human owns the decision required by the applicable doctrine boundary,
including any explicit override recorded through `decision`.

`inspect-architecture-scopes` is deterministic and read-only. It reports membership and recorded
approval state but has no reviewer, verdict, approval, or architecture-decision authority.

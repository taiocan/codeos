# DBA Doctrine — v6

DBA turns a human-approved specification into working, observable software. Detailed procedures,
prompts, templates, review rules, architecture mechanisms, file layouts, and tool instructions live
in their owning components rather than in this doctrine.

v6 is additive to v5: the authority ladder, the lifecycle, the Platform Baseline, the Codeos
Mechanics, and post-acceptance learning are unchanged. v6 adds three named governed workflows —
Solution Bootstrap, Feature Development, Operation & Learning — as the outer control structure
around the unchanged nine-stage lifecycle, and requires that progression through their checkpoints
be mechanically verified against real evidence rather than asserted. It does not add a new
lifecycle stage, a new approval, or a new source of product authority.

## Authority

The human's current explicit decision has highest authority over product meaning.

The approved **Solution Charter** defines the solution's problem, vision, measurable outcomes,
scope boundary, and System Constraints. Intent, Contract, and Event Schema are distinct parts of
one approved **Specification Package**. Together they define required behavior. Applicable approved
architecture defines project-level structural commitments but MUST NOT invent or override behavior.

Each decision has an owning level. A lower level MUST NOT silently redefine a decision owned above
it.

Runtime evidence and tests establish what the system currently does. They MUST NOT silently amend
approved requirements. Safety, authorization, and integrity requirements remain binding when
observed behavior violates them. Unresolved authority conflicts MUST be surfaced to the human.

## Solution Purpose

A Solution Charter MUST exist and be approved before the first Specification Package approval. It
carries one explicit human approval and no separate status or version field.

Each Charter outcome has a stable identity. An Intent records the outcomes it serves.

A material Charter change identifies potentially affected approved artifacts. Existing approvals
are not automatically invalidated, but affected artifacts MUST be reassessed before their next
implementation or acceptance. Recorded served outcomes identify impact from outcome changes.
Changes to scope, boundary, or System Constraints require an explicit impact assessment of affected
artifacts.

## Platform Baseline

A solution's approved architecture resolves three tiers by default: a persistence tier
(PostgreSQL), a backend tier (Rust), and a user-facing tier (Svelte), together with the runtime
needed to run them as one integrated system (Docker). A tier is absent only when the Solution
Charter explicitly and concisely records why it does not apply — for example, a solution with no
end user has no GUI tier. No separate exception-approval mechanism exists beyond the Charter's own
approval; recording the exception there is sufficient.

The Platform Baseline is a default, not an implementation-language constraint. It is distinct from,
and does not extend, the Implementation Profile: Implementation Profile governs preferred
implementation language within an already-resolved architecture; Platform Baseline governs which
architectural tiers the solution has.

## Governed Workflows

Three workflows enclose the nine-stage lifecycle:

- **Solution Bootstrap** — from an approved Charter to a runnable, integrated, minimally verified
  product baseline that a human has previewed, before any feature narrows attention to one
  capability. Usually performed once per solution.
- **Feature Development** — the repeated cycle that carries one capability from specification
  through implementation, the Early Development Preview, full verification, reconciliation, review,
  final human validation, and acceptance.
- **Operation & Learning** — the continuous handling of every material post-acceptance observation
  through exactly one classified route to a verified resolution.

Each workflow has an ordered set of checkpoints with a defined entry condition, required evidence,
required human decisions, exit condition, and valid failure or return routes. A later checkpoint
MUST NOT be treated as satisfied while a required earlier checkpoint is unresolved. Work performed
inside a checkpoint stays flexible; only the ordering between checkpoints is fixed.

A checkpoint's state MUST be derived from canonical evidence — approved artifacts and their
approval metadata, tests, runtime and review evidence, configuration, and explicitly recorded human
decisions — not from a manually maintained checklist. A checkpoint PASS may come from a currently
evaluated deterministic predicate or from durable canonical evidence; it MUST NOT be inferred from
an unpersisted historical command execution.

Mechanical tooling MAY establish that evidence exists, that approval metadata is valid, that
required test evidence exists and passed, that a required human decision was recorded, that a
required artifact version is current, and that a chosen route is valid. It MUST NOT infer whether
the product direction is good, whether a user interface is understandable, whether evidence is
persuasive, whether a Contract requirement is semantically correct, or which operational route an
observation belongs to. Those judgments remain with humans, agents, and the reviewer.

Mechanizing progression MUST NOT strengthen a substantive acceptance criterion. A checkpoint
establishes that the evidence a decision needs exists and is current; it never demands a stronger
result than the rest of this doctrine already requires. In particular, a completed reconciliation
that honestly records unresolved gaps is a completed reconciliation; whether those gaps permit
progression remains the existing acceptance decision.

### Decision Receipts

A **decision receipt** records that a workflow decision occurred and which governed inputs it was
bound to at the time. Receipts exist only for decisions that cannot be reconstructed from other
canonical evidence. A receipt is evidence of workflow progression; it is never a governing
artifact, never overrides or substitutes for the meaning of the Charter, a Specification Package,
an Architecture Scope, or any human-control boundary in this doctrine, and carries no product
authority. This is the same non-authority treatment this doctrine already gives the Module Design
Note and the Learning Register. A receipt ceases to establish its checkpoint when any governed
input it is bound to changes. Receipt format and the closed set of receipt-bearing decisions are
owned by the selected workflow-governance policy, not this doctrine.

## Feature Impact Accounting

A feature accounts for its impact on each Platform Baseline tier as changed or unchanged, with a
reason, rather than being required to touch every tier regardless of what it actually needs. When a
feature's Contract includes user-facing behavior, that behavior MUST be reachable through the GUI
tier inside the same bounded delivery cycle that implements it — a feature is not delivered while
its user-facing behavior exists only behind the backend. This is what keeps GUI-visible delivery
from accumulating as separate, later work behind a run of backend-only features.

## Early Development Preview

After a feature's first runnable implementation — across whichever tiers it actually touches —
passes basic integration smoke, and before the full verification loop proceeds, the human receives
a clearly labeled, unverified preview for a direction and UX check: *"Development Preview —
direction and UX review only; verification is incomplete."* This is not a lifecycle stage, not a
formal artifact, and not an acceptance gate. It exists to catch a wrong interpretation while it is
still cheap to fix, before expensive verification is sunk into it.

Preview feedback is not a channel for redefining approved meaning. Feedback that would change
approved behavior returns to the Specification Package for revision and human re-approval before
implementation continues. Feedback that concerns only implementation or UX choices within
already-approved behavior stays in implementation. This mirrors how runtime evidence is already
treated under Authority: it informs, and it never silently amends what was approved.

## Codeos Mechanics

The delivery and verification mechanics that define this variant — vertical-slice delivery, the
Early Development Preview, integration smoke, behavioral verification, repeatability verification,
data-integrity verification for a feature that persists data, browser-level acceptance for
GUI-visible outcomes, and human UX validation, together with the standing communication mechanics
(summary-first artifacts, reader-oriented writing, canonical terminology consistency) — are fixed
obligations. Their canonical names and semantics are owned by the selected Codeos Mechanics policy,
not restated here. A project's configuration may display them for transparency; it MUST NOT disable
or weaken one. Only a mechanic introduced later, outside this defining set, may be genuinely
project-selectable.

## Requirement Ownership and Verification

Quality requirements MUST be declared in a governed requirements source. Feature-specific quality
requirements belong to the Behavioral Contract. Cross-cutting quality requirements belong to the
Solution Charter's System Constraints. Architecture MAY respond to them but MUST NOT invent them.

System Constraint is the broader category. A cross-cutting quality requirement is one type of
System Constraint; regulatory obligations, mandated interoperability, deployment restrictions, and
externally imposed technology constraints are others and are not quality requirements.

Every quality requirement MUST define an appropriate verification method. Automated tests apply
where the requirement is testable; verification otherwise uses measurement, analysis, inspection,
review, or operational evidence. Reconciliation records the evidence the method produced, and
replay applies where replay is the method. For a feature with a GUI-visible outcome, the required
Codeos Mechanics apply in addition to, not instead of, this section.

Acceptance evidence MUST observe the boundary named by the claim it supports. Evidence of an
internal field, request value, event, or other proxy MUST NOT be used to claim a stronger observable
outcome that it does not demonstrate.

A performance measurement is admissible as evidence for a governed requirement only after the
harness demonstrates that the measured operation exercises the governed behavior. Diagnostic and
exploratory measurements remain ordinary engineering evidence until used for that governed claim.

A reconciliation claim MUST be no stronger than the cited observation. When the available evidence
proves only a proxy or a weaker outcome, reconciliation reports the remaining gap rather than
promoting the stronger claim.

Every System Constraint MUST have a defined verification route. An affected Specification Package
MUST demonstrate conformance when its implementation can affect that constraint.

Every quality threshold MUST state its workload, operating context, and rationale. A deliberately
new target does not require prior evidence; an unexplained number is not a requirement.

## Structural Ownership

Boundary scope decides authority; reversal cost decides visibility.

Architecture owns structural decisions that cross governed boundaries, affect multiple features or
components, or establish relied-on interfaces. Implementation owns feature-local decisions inside
those boundaries, including decisions that are costly to reverse. A feature-local decision that is
costly to reverse MUST be recorded in the implementation stage's output and reassessed at
reconciliation.

A **Module Design Note** is optional descriptive documentation of how an implementation module
currently works. It is explanatory only: it never governs behavior or structure, is never an input
to conformance, reconciliation, or approval, and a disagreement between it and the code means the
note is stale. Create one only when understanding the module from approved artifacts alone would
require reading substantial code. Update it only when the module's responsibility, major internal
flow, state model, important dependency, or consequential design choice changes — never for bug
fixes, renames, helper extraction, or formatting.

## Artifact Communication and Governance Transparency

Every substantial human-facing artifact opens with a short Summary immediately after its
frontmatter and declares which reader-oriented progression it uses, regardless of whether that
artifact type is governed. Governance controls approval and process weight; it does not control
readability. Exact frontmatter shape and Summary format are owned by the Downstream Project Layout
Contract and `reader-oriented-output.md`, not this doctrine.

One project configuration file is the single place naming the solution's Platform Baseline, the
active Codeos Mechanics, and each artifact type's governed or non-governed state. Charter, Intent,
Contract, and Event Schema are permanently governed and cannot be configured otherwise. Every other
artifact type is project-configurable. An artifact's governed state has exactly one authoritative
source — that configuration file — and is never restated inside the artifact itself.

Toggling an artifact type's governance changes its process weight only. It MUST NOT be read as
suspending a doctrine-level human-control guarantee: consequential architecture decisions still
require explicit human approval, and canonical terminology consistency still applies, regardless of
how the artifact carrying that evidence is configured. These guarantees are not represented as
configuration entries, so no configuration can appear to switch one off.

## DBA Lifecycle

Intent, Contract, and Event Schema MAY be drafted and revised together. No approval is required
between them. Before implementation, they MUST be mutually consistent and receive one explicit
human approval as a Specification Package.

A solution's first Specification Package MUST NOT enter the bounded delivery cycle until Solution
Bootstrap is complete. Later features do not repeat Bootstrap.

Package approval authorizes the bounded delivery cycle:

`Implementation → Tests → Development Evidence → Reconciliation → Replay`

Development Evidence is evidence produced before acceptance to prove the candidate implementation.
The cycle has no intermediate human gate beyond the Early Development Preview above, which is a
direction check, not an approval. Entry to the cycle, and final acceptance, additionally require
that the checkpoints preceding them have their evidence mechanically verified as present and
current. Final acceptance remains a human decision. A human MAY request an additional checkpoint at
any time.

Changes to approved behavior return to the affected Specification Package or targeted refinement.
Changes that establish or alter a project-level architectural boundary use the applicable
architecture policy. Behavior-neutral structural maintenance that does neither is ordinary
engineering outside the DBA lifecycle.

## Post-Acceptance Learning

An **Operational Observation** is a fact arising after acceptance, from real system use, that may
affect governed engineering truth.

Post-acceptance learning MUST return to the earliest governed authority whose truth must change.
Operational Observations and Learning Register entries are evidence, not governing requirements,
and cannot change approved behavior themselves.

| Operational finding | Returns to |
|---|---|
| Implementation defect against already-approved behavior | Targeted refinement, with verification proportional to the change — a presentation-only correction within approved behavior verifies through browser and human validation, not full behavioral re-verification |
| Requirement wrong or incomplete | Affected Specification Package |
| New user need or capability | New Intent |
| Architecture no longer satisfies approved requirements | Applicable architecture policy |
| Cross-cutting System Constraint changed | Solution Charter |
| Observed and deliberately not acted on | Closed with a recorded rationale |
| Material but not yet routable | Learning Register |

Every material Operational Observation MUST reach exactly one of these routes, and its resolution
MUST be verified before the observation is considered closed. The route is a human or authorized
agent judgment; tooling verifies only that a route was chosen, that it is valid, and that the
routed work's own evidence establishes resolution.

The **Learning Register** is an optional queue of material, unresolved observations that could
change governed engineering truth. It is not an operational log.

## Behavioral Constraints

Implementation MUST conform to the approved Specification Package and applicable architecture.
It MAY use normal internal structures, technical errors, validation, logging, and established
project patterns when they do not change approved behavior, authority, event semantics,
architecture, safety, authorization, or integrity.

Only Contract-approved behavioral failures may be exposed as governed failure outcomes. Only
Event-Schema-approved events may be emitted as governed events. Internal technical errors MAY be
richer, but MUST remain distinguishable from governed behavioral failures. Behavior MUST NOT be
hidden from the approved artifacts that govern it.

## Human Control and Implementation Freedom

One human decision approves the Solution Charter. One human decision approves the complete
Specification Package. Charter approval is additional to package approval and introduces no gate
inside the delivery cycle. The three specification artifacts record that same package decision
consistently; their status fields are distributed records, not separate gates. The approval applies
only while all three continue to represent the jointly approved specification.

Actions designated as controlled require human authorization. Package approval does not authorize
the agent to redefine the requested outcome, make an unresolved product or architecture decision,
or bypass an applicable safety, authorization, or integrity constraint.

### Doctrine Adapter Boundaries

These are the execution boundaries at which this doctrine's operational consequences are encoded:

- `purpose-approval` — Solution Charter approval
- `specification-approval` — Specification Package approval
- `bootstrap-entry` — entry to a solution's first feature delivery cycle, gated on Solution
  Bootstrap being mechanically verified as complete
- `delivery-entry` — entry to the bounded delivery cycle, additionally gated on the preceding
  Feature Development checkpoints being mechanically verified as present and current
- `final-acceptance` — final acceptance, additionally gated on the required verification,
  reconciliation, review, and final-validation evidence being mechanically verified as present and
  current
- `architecture-entry` — entry to project-level architecture synthesis

This list is authoritative for adapter membership. A boundary exists only where this doctrine
creates one, so the set is a property of this doctrine and changes only when it does. The
mechanical gating on `bootstrap-entry`, `delivery-entry`, and `final-acceptance` verifies evidence;
it does not add a human approval beyond the ones this doctrine already names.

## Escalation and Verification

Return to human governance when the work requires changing approved purpose, behavior, authority,
event semantics, project-level architecture, safety, authorization, or integrity.

Targeted refinement corrects an implementation that does not satisfy already-approved behavior. It
MUST NOT redefine intended behavior, requirements, or architecture; such changes return to their
owning authority. A repair that only restores conformance with already-approved meaning does not
require a new product decision, but it MUST receive verification proportional to its risk.

Runtime evidence used for verification MUST NOT be fabricated or silently rewritten. Tests,
development evidence, reconciliation, and replay determine whether implementation conforms. A
mismatch MUST be reported and resolved explicitly; observed behavior never becomes approved merely
because it occurred.

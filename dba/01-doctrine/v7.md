# DBA Doctrine — v7

DBA turns a human-approved specification into working, observable software that a human can
understand, review, and control.

Detailed procedures, policies, prompts, templates, formats, file layouts, and tool behavior belong
to their owning components.

v7 is additive to v6: the authority ladder, the lifecycle, the Platform Baseline, the Codeos
Mechanics, the three governed workflows, and post-acceptance learning are unchanged in substance.
v7 reorganizes the doctrine into an explicit three-level hierarchy — itself a normative
meta-governance addition — and adds one new constitutional invariant, **D10 — human reviewability**.
It adds no lifecycle stage, no new approval, and no new source of product authority.

One rule changes ownership level without changing its product effect: the explicit requirement that
a substantial artifact *declare* its `reader_model`, and the specific placement of the Summary
block, move from v6 doctrine prose to the selected Reader Output policy and the Downstream Project
Layout Contract. The underlying obligations — `summary_first` and reader-oriented writing — remain
fixed Codeos Mechanics under D12, and D10 carries the reviewability principle. The obligation still
binds; the layer that may revise its detailed wording is now policy.

## How to read this doctrine

Every normative chapter uses three levels:

- **CRITICAL DOCTRINE** — a constitutional invariant. Violating it means the process is no longer
  conformant with this DBA doctrine.
- **REQUIRED CONSEQUENCE** — what MUST follow from that doctrine, without prescribing unnecessary
  implementation detail.
- **POLICY MECHANISM** — the current Codeos mechanism used to enforce or demonstrate the doctrine.
  It has no independent product authority and MAY change without a doctrine revision as long as the
  doctrine and its consequences remain true.

Precedence: **CRITICAL DOCTRINE → REQUIRED CONSEQUENCE → POLICY MECHANISM**. A lower level MUST NOT
weaken or reinterpret a higher level. This three-level model is itself normative: it is the
authority ladder for every rule below, and the Change Classification section governs which level
owns which kind of change.

controlled workflow → user-facing delivery and review → evidence and integrity → learning and
evolution.

## A. Meaning and Authority

### 1. Authority

**CRITICAL DOCTRINE — D1.** Approved meaning may change only at the authority that owns it.

**REQUIRED CONSEQUENCE.**

- The human's current explicit decision has highest authority over product meaning.
- The approved Solution Charter owns the solution's problem, vision, measurable outcomes, scope
  boundary, and System Constraints.
- Intent, Contract, and Event Schema form one approved Specification Package and together own
  required feature behavior.
- Applicable approved architecture owns project-level structural commitments. It MUST NOT invent or
  override product behavior.
- Runtime evidence and tests establish what the system currently does. They MUST NOT silently amend
  approved meaning. Safety, authorization, and integrity requirements remain binding when observed
  behavior violates them.
- A lower authority MUST NOT silently redefine a decision owned above it.
- Unresolved authority conflicts MUST be surfaced to the human.

**POLICY MECHANISM.** Current Codeos mechanisms include Charter approval, joint Specification
Package approval, consequential-architecture approval, approval metadata, adapter-boundary checks,
reconciliation, and reviewer checks against current approved inputs. These mechanisms enforce
authority; they create no additional product authority.

### 2. Solution Purpose

**CRITICAL DOCTRINE — D2.** Feature work must remain traceable to approved solution purpose, and
material purpose changes require reassessment of affected work.

**REQUIRED CONSEQUENCE.**

- A Solution Charter MUST be approved before the first Specification Package is approved. It carries
  one explicit human approval and no separate status or version field.
- Each Charter outcome has a stable identity. Each Intent records the outcomes it serves, and
  recorded served outcomes identify impact from outcome changes.
- A material Charter change MUST identify potentially affected approved artifacts. Existing
  approvals are not automatically invalidated, but affected artifacts MUST be reassessed before
  their next implementation or acceptance.
- Changes to scope, boundary, or System Constraints require an explicit impact assessment of
  affected artifacts.

**POLICY MECHANISM.** Current Codeos mechanisms include the Solution Charter, stable outcome
identities, served-outcome mappings, Charter impact assessment, and workflow checks before affected
implementation or acceptance.

## B. Solution Structure

### 3. Platform Baseline

**CRITICAL DOCTRINE — D3.** A normal DBA solution resolves PostgreSQL persistence, Rust backend,
Svelte user-facing, and Docker integrated-runtime tiers unless the approved Charter explicitly
states that a tier does not apply.

**REQUIRED CONSEQUENCE.**

- A solution's approved architecture resolves a persistence tier (PostgreSQL), a backend tier
  (Rust), and a user-facing tier (Svelte), together with the runtime needed to run them as one
  integrated system (Docker), by default.
- A tier is absent only when the Solution Charter explicitly and concisely records why it does not
  apply — for example, a solution with no end user has no GUI tier.
- Charter approval is sufficient for the exception; no separate exception-approval mechanism
  exists.
- Platform Baseline governs which architectural tiers the solution has. The Implementation Profile
  governs preferred implementation language within an already-resolved architecture; it is distinct
  from, and does not extend, the Platform Baseline.

**POLICY MECHANISM.** Current Codeos mechanisms include Platform Baseline resolution during
architecture synthesis, `codeos.yaml`, the PostgreSQL + Axum/SQLx + SvelteKit + Docker reference
skeleton, the initializer, and configuration validation.

### 4. Structural Ownership

**CRITICAL DOCTRINE — D4.** Architecture owns consequential cross-boundary structure; implementation
owns feature-local structure.

**REQUIRED CONSEQUENCE.**

- Boundary scope decides authority; reversal cost decides visibility.
- Architecture owns structural decisions that cross governed boundaries, affect multiple features
  or components, or establish relied-on interfaces.
- Implementation owns feature-local decisions inside those boundaries, including decisions that are
  costly to reverse. High reversal cost increases required visibility; it does not by itself
  transfer authority to architecture.
- A costly-to-reverse feature-local decision MUST be recorded in the implementation stage's output
  and reassessed at reconciliation.
- A Module Design Note is optional descriptive documentation of how an implementation module
  currently works. It never governs behavior or structure, is never an input to conformance,
  reconciliation, or approval, and a disagreement between it and the code means the note is stale.
  Create one only when understanding the module from approved artifacts alone would require reading
  substantial code. Update it only when the module's responsibility, major internal flow, state
  model, important dependency, or consequential design choice changes — never for bug fixes,
  renames, helper extraction, or formatting.

**POLICY MECHANISM.** Current Codeos mechanisms include the Architecture Synthesis policy,
Architecture Scope, `architecture-entry`, implementation output for consequential local decisions,
and the module-design-note template.

## C. Controlled Workflow and Human Authority

### 5. Governed Workflow Progression

**CRITICAL DOCTRINE — D5.** Workflow progression must be proven from current evidence; it must not
be asserted.

**CRITICAL DOCTRINE — D6.** Mechanical tooling verifies workflow state; it must not make semantic
product judgments.

**REQUIRED CONSEQUENCE.**

DBA governs three workflows:

- **Solution Bootstrap** — establishes a runnable, integrated, minimally verified baseline that a
  human has previewed before the first feature enters delivery. Usually performed once per
  solution.
- **Feature Development** — carries one capability from specification through implementation,
  preview, verification, reconciliation, review, final validation, and acceptance.
- **Operation & Learning** — routes each material post-acceptance observation to a verified
  resolution.

For all three:

- checkpoints are ordered, each with a defined entry condition, required evidence, required human
  decisions, exit condition, and valid failure or return routes;
- a later checkpoint MUST NOT pass while a required earlier checkpoint is unresolved;
- work inside a checkpoint remains flexible; only the ordering between checkpoints is fixed;
- checkpoint state comes only from currently evaluated deterministic checks, durable canonical
  evidence, or explicitly recorded decisions — never from a manually maintained checklist;
- an unpersisted historical command result MUST NOT be treated as durable proof;
- mechanizing progression MUST NOT strengthen an existing substantive acceptance criterion.

Mechanical tooling MAY establish that required evidence exists, that approval metadata is valid,
that a required test result exists and passed, that a required decision was recorded, that evidence
is current, and that a selected route is valid.

Mechanical tooling MUST NOT decide whether product direction is correct, whether a user interface
is good or understandable, whether evidence is persuasive, whether a requirement is semantically
correct, or which operational route applies. Those judgments remain with humans, agents, and the
reviewer.

A reconciliation that truthfully records unresolved gaps may still be complete. Whether those gaps
permit acceptance remains the acceptance decision.

A decision receipt records that a workflow decision occurred and which governed inputs it was bound
to at the time. It is evidence of workflow progression only: it is never a governing artifact,
never overrides or substitutes for the meaning of the Charter, a Specification Package, an
Architecture Scope, or any human-control boundary in this doctrine, and carries no product
authority — the same non-authority treatment this doctrine gives the Module Design Note and the
Learning Register. A receipt ceases to establish its checkpoint when any governed input it is bound
to changes.

**POLICY MECHANISM.** Current Codeos mechanisms include the Workflow Governance, Workflow
Bootstrap, Workflow Feature, and Workflow Operation policies; `codeos-workflow status`,
`codeos-workflow check`, `codeos-workflow next`, and restricted decision-receipt recording; and
binding-hash staleness checks. Receipt format, the permitted receipt-bearing decisions, the
bindings, and the staleness rules belong to the Workflow Governance policy, not this doctrine.

### 6. Controlled Delivery and Acceptance

**CRITICAL DOCTRINE — D7.** Delivery begins from approved meaning and required workflow evidence;
final acceptance remains a human decision.

**REQUIRED CONSEQUENCE.**

- Intent, Contract, and Event Schema MAY be drafted and revised together with no approval between
  them. Before implementation they MUST be mutually consistent and receive one explicit human
  approval as a Specification Package.
- A solution's first Specification Package MUST NOT enter the bounded delivery cycle until Solution
  Bootstrap is complete. Later features do not repeat Bootstrap.
- Package approval authorizes the bounded delivery cycle:
  `Implementation → Tests → Development Evidence → Reconciliation → Replay`. Development Evidence is
  evidence produced before acceptance to prove the candidate implementation.
- The cycle has no intermediate human gate beyond the Early Development Preview, which is a
  direction check, not an approval.
- Entry to the cycle, and final acceptance, additionally require that the preceding checkpoints
  have their required evidence mechanically verified as present and current.
- Final acceptance remains a human decision. A human MAY request an additional checkpoint at any
  time.
- Changes to approved behavior return to the affected Specification Package or targeted refinement.
  Changes that establish or alter a project-level architectural boundary use the applicable
  architecture policy. Behavior-neutral structural maintenance that does neither is ordinary
  engineering outside the DBA lifecycle.
- Actions designated as controlled require their designated human authorization. Package approval
  does not authorize an agent to redefine the requested outcome, make an unresolved product or
  architecture decision, or bypass an applicable safety, authorization, or integrity constraint.

**POLICY MECHANISM.** Doctrine is operationalized at the adapter boundaries listed under Doctrine
Adapter Boundaries below. Mechanical gating verifies evidence at those boundaries; it adds no human
approval.

## D. Product Delivery and Human Review

### 7. Vertical Product Delivery

**CRITICAL DOCTRINE — D8.** A user-facing feature is not delivered until its approved behavior is
reachable through the running product in the same bounded delivery cycle.

**REQUIRED CONSEQUENCE.**

- Every feature accounts for its impact on each Platform Baseline tier as changed or unchanged,
  with a reason. A feature is not required to change every tier.
- When an approved Contract contains user-facing behavior, that behavior MUST be reachable through
  the GUI tier within the same bounded delivery cycle that implements it.
- Backend-only completion MUST NOT be represented as delivery of GUI-visible behavior. This keeps
  GUI-visible delivery from accumulating as separate, later work behind a run of backend-only
  features.

**POLICY MECHANISM.** Current Codeos mechanisms include Feature Impact Accounting, Stage 4
vertical-slice guidance, integrated PostgreSQL ↔ Rust ↔ Svelte smoke checks, and browser or
Playwright verification where applicable.

### 8. Early Direction Correction

**CRITICAL DOCTRINE — D9.** Product direction must be exposed to the human before expensive
verification, without allowing preview feedback to silently change approved meaning.

**REQUIRED CONSEQUENCE.**

- After a feature's first runnable implementation passes basic integration smoke, and before the
  full verification loop proceeds, the human receives a clearly labeled, unverified preview:
  *"Development Preview — direction and UX review only; verification is incomplete."*
- The preview is not a lifecycle stage, not a formal artifact, and not an acceptance gate.
- Behavior-changing feedback routes to Specification Package revision, human re-approval, then
  continued implementation. Implementation-only or UX-only feedback within already-approved
  behavior stays in implementation and repeats the preview as needed.
- Preview feedback MUST NOT silently redefine approved meaning.

**POLICY MECHANISM.** Current Codeos mechanisms include the Early Development Preview checkpoint,
preview decision receipts, F4 gating, and Stage 4 and Stage 5 routing rules.

### 9. Human Reviewability and Semantic Structure

**CRITICAL DOCTRINE — D10.** Human-facing meaning must be hierarchically structured and
semantically separable enough for efficient understanding and review. Correct content that a human
cannot efficiently absorb, distinguish, and review is insufficient for DBA human control.

**REQUIRED CONSEQUENCE.**

1. **Whole before detail** — the main result, decision, or purpose precedes supporting detail.
2. **Semantic separation** — distinct reader questions or domains are separated into stable
   sections and paragraphs.
3. **Explicit meaning** — the relationships between decision, reason, evidence, uncertainty, and
   action are made visible rather than compressed together.
4. **Progressive understanding** — new meaning builds from established context and uses the
   project's canonical terminology.
5. **Navigable status and detail** — decisions, observations, evidence, assumptions, gaps, and next
   actions remain distinguishable, and summaries orient the reader toward deeper evidence rather
   than replacing it.

The same principles apply to substantial governed and non-governed artifacts, generated reports,
reviewer and workflow output, and substantial inline agent responses. Metadata requirements apply
only where the selected policy requires them.

**POLICY MECHANISM.** The Reader Output policy selected by the active DBA configuration owns the
detailed rules: reader-model progressions, section and status separation, navigable detail,
sentence continuity, Summary placement, `reader_model` declaration, inline-response handling, and
reviewer expectations. Mechanical tooling verifies only cheap structural properties; it MUST NOT
claim that prose is semantically easy to understand. That judgment remains with the producing
agent, the reviewer, and the human.

## E. Evidence, Governance, and Behavioral Integrity

### 10. Evidence and Verification

**CRITICAL DOCTRINE — D11.** A governed claim must have evidence appropriate to the boundary and
strength of that claim.

**REQUIRED CONSEQUENCE.**

- Quality requirements MUST originate in a governed requirements source. Feature-specific
  requirements belong to the Behavioral Contract; cross-cutting requirements belong to the Solution
  Charter's System Constraints. Architecture MAY respond to requirements but MUST NOT invent them.
- System Constraint is the broader category: a cross-cutting quality requirement is one type,
  alongside regulatory obligations, mandated interoperability, deployment restrictions, and
  externally imposed technology constraints.
- Every governed requirement MUST define an appropriate verification method — an automated test
  where the requirement is testable, otherwise measurement, analysis, inspection, review, or
  operational evidence. Reconciliation records the evidence the method produced; replay applies
  where replay is the method. Every System Constraint MUST have a defined verification route, and
  an affected Specification Package MUST demonstrate conformance when its implementation can affect
  that constraint.
- Evidence MUST observe the boundary named by the claim it supports. A proxy — an internal field,
  request value, event, or weaker outcome — MUST NOT be used to claim a stronger observable result.
- A reconciliation claim MUST be no stronger than its cited observation; when evidence proves only
  a proxy or a weaker outcome, reconciliation reports the remaining gap.
- A performance measurement is admissible as evidence for a governed requirement only after the
  measured operation is shown to exercise the governed behavior. Diagnostic and exploratory
  measurements remain ordinary engineering evidence until used for that governed claim.
- Every quality threshold MUST state its workload, operating context, and rationale. A deliberately
  new target does not require prior evidence; an unexplained number is not a requirement.
- When persistence is affected, data-integrity verification MUST demonstrate the applicable
  persisted-state invariants.
- For a feature with a GUI-visible outcome, the required Codeos Mechanics apply in addition to, not
  instead of, this section.

**POLICY MECHANISM.** Current Codeos mechanisms include the Codeos Mechanics policy, behavioral
tests, repeatability verification, `data_integrity: always_when_persistence`, real PostgreSQL
integration testing where database behavior matters, component and browser verification, Playwright
integrated journeys for GUI-visible outcomes, conditional performance, security, accessibility,
concurrency, and migration verification, and reconciliation evidence mapping.

### 11. Governance and Fixed Mechanics

**CRITICAL DOCTRINE — D12.** Project configuration and policy mechanisms must not disable or weaken
doctrine-level controls.

**REQUIRED CONSEQUENCE.**

- Solution Charter, Intent, Contract, and Event Schema are permanently governed. Other artifact
  types may be project-configurable.
- Changing an artifact type's governance changes process weight only. It MUST NOT be read as
  suspending a doctrine-level human-control guarantee: consequential architecture decisions still
  require explicit human approval, and canonical terminology consistency still applies, regardless
  of how the artifact carrying that evidence is configured.
- The defining Codeos Mechanics are mandatory and cannot be disabled by project configuration:
  vertical-slice delivery, the Early Development Preview, integration smoke, behavioral
  verification, repeatability verification, data-integrity verification when persistence is
  affected, browser-level verification for GUI-visible outcomes, human UX validation, summary-first
  communication, reader-oriented writing, and canonical terminology consistency. Only a mechanic
  introduced later, outside this defining set, may be genuinely project-selectable.
- Each artifact type has exactly one authoritative governance source — the project configuration
  file — and its governed state is never restated inside the artifact itself. These guarantees are
  not represented as configuration entries, so no configuration can appear to switch one off.

**POLICY MECHANISM.** Current Codeos mechanisms include `codeos.yaml`, project-configuration
validation, the selected Codeos Mechanics policy, artifact templates, the selected Reader Output
policy, and terminology-consistency checks. Canonical mechanic names and detailed semantics belong
to the selected policy.

### 12. Behavioral Integrity

**CRITICAL DOCTRINE — D13.** Implementation must conform to approved behavior and applicable
architecture; observed behavior never becomes approved merely because it occurred.

**REQUIRED CONSEQUENCE.**

- Normal internal structures, technical errors, validation, logging, and established project
  patterns are permitted when they do not change approved behavior, authority, event semantics,
  architecture, safety, authorization, or integrity.
- Only Contract-approved behavioral failures may be exposed as governed failure outcomes. Only
  Event-Schema-approved events may be emitted as governed events.
- Internal technical errors MAY be richer but MUST remain distinguishable from governed behavioral
  failures. Behavior MUST NOT be hidden from the approved artifacts that govern it.
- Runtime evidence used for verification MUST NOT be fabricated or silently rewritten.
- A mismatch between approved truth and observed behavior MUST be reported and resolved explicitly.

**POLICY MECHANISM.** Current Codeos mechanisms include Contract and Event Schema checks, behavior
and replay tests, development evidence, reconciliation, reviewer assessment, and targeted
refinement for implementation defects.

## F. Learning and Evolution

### 13. Operation and Learning

**CRITICAL DOCTRINE — D14.** Every material post-acceptance observation must reach a governed,
verified resolution or an explicitly justified retained or closed state.

**REQUIRED CONSEQUENCE.**

- A material Operational Observation is a fact arising after acceptance, from real system use, that
  may affect governed engineering truth.
- Each material observation MUST reach exactly one valid route:

  | Operational finding | Required route |
  |---|---|
  | Implementation defect against already-approved behavior | Targeted refinement, with verification proportional to the change |
  | Requirement wrong or incomplete | Affected Specification Package |
  | New user need or capability | New Intent |
  | Architecture no longer satisfies approved requirements | Applicable architecture policy |
  | Cross-cutting System Constraint changed | Solution Charter |
  | Observed and deliberately not acted on | Closed with a recorded rationale |
  | Material but not yet routable | Learning Register |

- Proportional verification means a presentation-only correction within approved behavior verifies
  through browser and human validation, not full behavioral re-verification.
- The route is a human or authorized-agent judgment. Tooling verifies only that exactly one valid
  route was selected, that the routed work produced the resolution evidence that route requires,
  and that closure is justified by that evidence.
- Operational Observations and Learning Register entries are evidence, not governing requirements,
  and cannot change approved behavior by themselves. The Learning Register is an optional queue of
  material, unresolved observations that could change governed engineering truth; it is not an
  operational log.

**POLICY MECHANISM.** Current Codeos mechanisms include the Workflow Operation policy,
operational-observation identity and evidence, route decision receipts, proportional verification,
`no_action` closure rationale, and Learning Register handling.

### 14. Escalation to Owning Authority

**CRITICAL DOCTRINE — D15.** A change that alters governed meaning returns to the authority that
owns that meaning.

**REQUIRED CONSEQUENCE.**

- Return to human governance when the work requires changing approved purpose, approved behavior,
  authority, governed event semantics, project-level architecture, safety, authorization, or
  integrity.
- Targeted refinement may restore conformance to already-approved meaning without a new product
  decision, but it MUST NOT redefine intended behavior, requirements, or architecture, and it MUST
  receive verification proportional to its risk.

**POLICY MECHANISM.** Current Codeos mechanisms include Specification Package revision, Charter
revision and impact assessment, architecture reassessment, targeted refinement, and workflow
routing from previews and Operational Observations.

## Doctrine Operationalization

### Doctrine Adapter Boundaries

These are the execution boundaries at which this doctrine's operational consequences are encoded:

- `purpose-approval` — Solution Charter approval
- `specification-approval` — Specification Package approval
- `bootstrap-entry` — entry to a solution's first feature delivery cycle, gated on Solution
  Bootstrap being mechanically verified as complete
- `delivery-entry` — entry to the bounded delivery cycle, additionally gated on the preceding
  Feature Development checkpoints being mechanically verified as present and current
- `final-acceptance` — final acceptance, additionally gated on the required verification,
  reconciliation, review, and final-validation evidence being mechanically verified as present and
  current
- `architecture-entry` — entry to project-level architecture synthesis

This list is authoritative for adapter membership. A boundary exists only where this doctrine
creates a real human-control or progression boundary, so the set is a property of this doctrine and
changes only when it does. Mechanical checks inside a workflow do not create new doctrine adapters,
and the mechanical gating on `bootstrap-entry`, `delivery-entry`, and `final-acceptance` verifies
evidence without adding a human approval beyond the ones this doctrine already names.

## Applying the Three-Level Model in Codeos

**Example 1 — Workflow progression.**
CRITICAL DOCTRINE: progression must be proven from evidence.
REQUIRED CONSEQUENCE: F5 cannot pass while F4 is unresolved.
POLICY MECHANISM: `codeos-workflow` evaluates the workflow contract, current evidence, hashes, and
decision receipts.

**Example 2 — Early Development Preview.**
CRITICAL DOCTRINE: product direction must be exposed before expensive verification without silently
changing approved meaning.
REQUIRED CONSEQUENCE: behavior-changing preview feedback returns to Specification Package revision;
implementation or UX-only feedback remains in implementation.
POLICY MECHANISM: the Feature Workflow policy defines F4 routes; `codeos-workflow` records and
checks the preview decision and its bindings.

**Example 3 — Data integrity.**
CRITICAL DOCTRINE: a governed claim must have evidence appropriate to the claim.
REQUIRED CONSEQUENCE: a feature that persists or changes data must demonstrate applicable
persisted-state invariants.
POLICY MECHANISM: Codeos Mechanics selects `data_integrity: always_when_persistence`; Stage 5 uses
real PostgreSQL and applicable migration, constraint, and transaction tests.

**Example 4 — Architecture.**
CRITICAL DOCTRINE: architecture owns consequential cross-boundary structure; implementation owns
feature-local structure.
REQUIRED CONSEQUENCE: a feature-local but expensive-to-reverse choice is made visible and
reassessed, but does not become architecture merely because reversal is costly.
POLICY MECHANISM: the Architecture Synthesis policy determines when `architecture-entry` applies;
implementation output records consequential local decisions.

**Example 5 — Operation and Learning.**
CRITICAL DOCTRINE: every material operational observation must reach a governed resolution or a
justified retained or closed state.
REQUIRED CONSEQUENCE: an observation cannot close without exactly one valid human or
authorized-agent route and the evidence that route requires.
POLICY MECHANISM: the Workflow Operation policy defines O1–O5; route decisions are non-authoritative
receipts; `codeos-workflow` validates the route and the closure evidence.

**Example 6 — Human reviewability.**
CRITICAL DOCTRINE: human-facing meaning must be hierarchically structured and semantically
separable enough for efficient review.
REQUIRED CONSEQUENCE: a substantial artifact or response exposes its main result first, separates
distinct semantic domains, keeps decisions, evidence, gaps, and actions distinguishable, and
follows an appropriate reader progression.
POLICY MECHANISM: the selected Reader Output policy, summary-first templates, `reader_model`, prompt
rules, structural preflight, and reviewer semantic-readability assessment.

## Change Classification

The hierarchy determines the correct owner and version boundary for a change.

| Change | Normal owner |
|---|---|
| Changes a Critical Doctrine | New doctrine version |
| Changes a mandatory workflow consequence while preserving doctrine | Workflow or policy version; doctrine changes only if its own normative text changes |
| Changes evidence format, hashes, receipt schema, commands, prompts, formatting, or test execution | Policy, tool, or prompt version only |
| Changes descriptive guidance without affecting conformance | Guidance only |

Examples:

- Changing the receipt JSON format → policy or tool change.
- Changing an F4 evidence binding → Workflow Governance policy change.
- Changing whether F5 may pass before F4 → workflow contract or policy change.
- Changing the rule that progression must be evidence-proven → doctrine change.
- Changing how a human preview is displayed → prompt or UI mechanism change.
- Changing a Summary template while preserving D10 → communication policy or template change.
- Changing supported reader-model mechanics while preserving D10 → Reader Output policy change.
- Removing human final acceptance → doctrine change.

This separation is intentional: Codeos is strict about invariants and flexible about mechanisms.
